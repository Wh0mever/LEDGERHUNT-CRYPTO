# Тестовые сценарии с известным ответом (Этап 2, пункт 4.6)

Набор нужен, чтобы проверять трассировщик автоматически: у каждого сценария заранее известен правильный ответ, а данные для него лежат в тех же сырых форматах, что отдают реальные источники. Трассировщика ещё нет: здесь подготовлены сами сценарии, схема ответа, оценщик по правилам владельцев и отложенный набор.

Задание: [stage-2-decisions.md](../spec/stage-2-decisions.md), разделы 1.5 и 4.6; критерии — [Промпт 3](../spec/prompt-3-success-criteria.md), разделы 2 и 9.

## Как запускать

Из корня репозитория:

```
python run_stage2.py --only scenarios
```

Команда пересобирает набор для разработки, проверяет каждый сценарий, проверяет целостность отложенного набора, сравнивает форматы с реальными ответами и пишет результат в `results/stage-2/scenarios/<время UTC>/`. Повторный запуск даёт побайтно те же файлы: в итоге прогона это видно по строке «изменения относительно прошлой версии: False» и по совпадению `tree_sha256` в `tests/scenarios/dev/manifest.json`.

Остальные команды (внутри `.venv`):

| Команда | Что делает |
|---|---|
| `python -m ledgerhunt.scenarios generate` | только пересобрать набор для разработки |
| `python -m ledgerhunt.scenarios validate --split dev` | только проверить набор |
| `python -m ledgerhunt.scenarios score --split dev --candidates <каталог>` | оценить результаты трассировщика: в каталоге файлы `<scenario_id>.json` в схеме результата |
| `python -m ledgerhunt.scenarios verify-holdout` | проверить хеши отложенного набора |
| `python -m ledgerhunt.scenarios create-holdout --seed <значение> --out <каталог>` | только для владельцев: создать свой отложенный набор |
| `python -m pytest tests/test_scenarios.py` | модульные тесты генератора, форматов и оценщика |

## Категории

Первые семь — из раздела 9 Промпта 3, мосты и отказы источников добавлены по решению владельцев (разделы 2.3 и 4.6). В каждой категории 6 вариантов; набор для разработки содержит каждый вариант один раз, отложенный — 3 случайных варианта на категорию со своими случайными параметрами.

| Категория | Варианты |
|---|---|
| direct — прямые переводы | один адрес; цепочка с комиссией за аренду энергии; два платежа жертве и вывод двумя частями; кража через ранее выданное разрешение (transferFrom); пополнение TRX для газа как шум; конец на известном сервисе |
| fan_out — разветвления | 2–5 ветвей; двухуровневое дерево; 3–5 переводов в одной транзакции (ключ ребра — TXID + event_index); ровно 1% на сборщик комиссии; разветвление и повторное слияние без чужих средств; ветка на биржу |
| merge — объединения со смешением | адрес с чужими средствами до кражи; чужие средства после прихода украденных, до вывода; чужие средства после ухода украденных (смешения нет); две ветки на один адрес с чужими средствами; прошлая история с нулевым балансом (смешения нет); смешанные средства уходят на биржу |
| long_chain — длинные цепочки | 10–14 переходов; 15–25 переходов с комиссиями (глубина 30); цепочка отщеплений; 25–30 переходов при глубине 12; длинная цепочка до биржи; длинная цепочка до моста |
| cycles — повторы и циклы | A→B→C→A→D; пинг-понг; ветки сходятся на одном адресе разными переводами; частичный возврат; повторное посещение с комиссией; часть средств возвращается жертве |
| exchange — биржи | депозит и свип на горячий кошелёк; два депозита и один свип; две биржи; быстрая полная пересылка на неизвестный адрес (не биржа); перевод прямо на горячий кошелёк; депозит с прошлой историей и свипом через часы |
| incomplete_data — неполные данные | нулевые переводы и пыль с похожих адресов (отравление); неуспешные транзакции OUT_OF_ENERGY и REVERT; пропущенная страница с продолжением маршрута; пропущенная страница без потери маршрута; пробел в индексе (перевод не виден в списке, баланс показывает расхождение); смешанный шум |
| bridge — выход в мост | USDT0 (LayerZero OFT) в поддерживаемую сеть (dstEid 30101); в неподдерживаемую (30110); сообщение не найдено в LayerZero Scan; перевод в контракт неподдерживаемого моста; одна ветка в мост, другая на биржу; схема как в case-001 (комиссия, 1%, мост) |
| source_failure — отказы источников | список переводов адреса отвечает 503; постоянный 429 на одной ветке; второй источник квитанций недоступен; LayerZero Scan недоступен; второй источник не отдаёт часть квитанций; недоступен эндпоинт событий TronGrid |

Длины маршрутов: в категории long_chain основной маршрут 12–19 переходов (12 — у варианта, обрезанного глубиной 12), во всём наборе 97 ожидаемых маршрутов.

## Из чего состоит сценарий

```
tests/scenarios/dev/dev-017/
  input.json      то, что получает трассировщик: TXID кражи, глубина, метки, поддерживаемые мосты, где лежат ответы
  expected.json   правильный ответ (схема ниже) и meta: категория, вариант, описание
  world.json      полная «правда» генератора: все транзакции, отказы, сообщения моста (трассировщику читать нельзя)
  http-store/     сырые ответы источников: index.jsonl + objects/<sha256>
```

`input.json` нейтрален: идентификаторы непрозрачны (`dev-017`, `hold-005`), категории и подсказок в нём нет — они только в `expected.json`.

### Сырые ответы

`http-store/` записан настоящими клиентами фундамента (`TronGridClient`, `TronNodeClient`, `LayerZeroScanClient`) через `RecordingClient`, у которого вместо сети подставлен сервер сценария (`ScenarioServer`). Поэтому ключи запросов, параметры, пагинация через `fingerprint` и тела ответов именно такие, какие трассировщик получит от клиентов. Воспроизведение:

```python
http = RecordingClient(mode="replay", store_dir="tests/scenarios/dev/dev-017/http-store")
tg = TronGridClient(http, api_key=None)
```

Записанный профиль запросов `scenario-profile/1` — по каждому адресу и каждой транзакции мира сценария:

| Источник | Запрос |
|---|---|
| TronGrid v1 | `/v1/accounts/{addr}/transactions/trc20` (USDT, limit=200, по возрастанию времени, все страницы); `/v1/accounts/{addr}/transactions` (все страницы); `/v1/transactions/{txid}/events` |
| TronGrid, API узла | `wallet/gettransactionbyid`, `walletsolidity/gettransactioninfobyid`, `wallet/triggerconstantcontract` (balanceOf) |
| Второй оператор (PublicNode) | `wallet/gettransactionbyid`, `walletsolidity/gettransactioninfobyid` |
| LayerZero Scan | `/v1/messages/tx/{hash}`, `/v1/messages/guid/{guid}` |

Запрос с другими параметрами в режиме replay даст `ReplayMiss`. Для произвольных запросов (другой `limit`, порядок, фильтры по времени, другой хост узла) трассировщик может работать прямо с сервером сценария: `ScenarioServer(World.load(".../world.json")).transport()` подставляется в `RecordingClient(transport=...)`.

### Насколько форматы совпадают с реальными

Сравнивались структуры ключей синтетических ответов и реальных ответов из `data/http-store/` (записаны 2026-10-14 по транзакциям case-001):

| Эндпоинт | Результат сравнения |
|---|---|
| TronGrid TRC20-переводы | совпадает |
| TronGrid события транзакции | совпадает; лишние только поля события Approval (реального образца Approval в хранилище нет) |
| `gettransactionbyid` | совпадает |
| `gettransactioninfobyid` | совпадает; лишние поля только у неуспешных транзакций (`result`, `resMessage`) и переводов TRX (`receipt.net_usage`) — реальных образцов этих типов нет |
| `triggerconstantcontract` | совпадает |
| TronGrid транзакции аккаунта | совпадает, кроме полей пагинации (синтетические списки аккаунтов короче 200 строк) и `fee_limit` у вызовов контрактов (в реальных образцах только TRX и делегирование энергии) |
| LayerZero Scan, сообщение | совпадает |

Дополнительно модульные тесты проверяют побайтно: кодирование `raw_data` воспроизводит реальную транзакцию кражи `98f3ffca…` и её TXID (TXID = sha256 от protobuf `raw_data`, поэтому синтетические TXID самосогласованы); guid сообщения LayerZero, payload пакета, payloadHash и сигнатуры событий OFTSent, PacketSent, ExecutorFeePaid, DVNFeePaid совпадают с реальной отправкой USDT0 `b49b0157…`.

Что синтетическое и что допущено:
- все адреса EOA, TXID, guid, суммы и подписи синтетические; подписи невалидны;
- адреса инфраструктурных контрактов настоящие: USDT `TR7NHq…`, USDT0 OFT `TFG4wB…`, LayerZero endpoint и библиотека отправки, DVN и исполнитель;
- имена бирж и сервисов вымышленные (SynthEx Alpha/Beta/Gamma, SynthEnergy Rent, SynthPay, SynthBridge X), чтобы синтетика не выглядела как реальные метки;
- тела ошибок (503, 429, 500) — короткий текст с пометкой «synthetic»: реальные тела ошибок провайдеров не записывались;
- допущения, не проверенные замером: TronGrid по умолчанию отдаёт 20 строк и сортирует по убыванию времени; список транзакций аккаунта содержит транзакции, где адрес подписант или получатель TRX; для неизвестной транзакции эндпоинт событий отдаёт пустой список; поля квитанции неуспешной транзакции взяты из описания java-tron;
- имена сетей для eid, кроме 30101 (Ethereum, подтверждено case-001), не проверялись; 30110 используется как «неподдерживаемая сеть»;
- сторону Ethereum для поддерживаемого моста генератор не создаёт: адрес получателя и TXID на стороне назначения берутся из сообщения LayerZero Scan. Реальный участок Ethereum (Rango, NEAR Intents) есть только в case-001;
- записанное хранилище не может содержать тайм-аут (ответ, которого не было): отказ записан как HTTP 503, 429 или 500. Тайм-аут сервер сценария умеет отдавать только при прямой работе (`mode: timeout` в правиле отказа).

## Схема ответа

Одна схема (`ledgerhunt.scenario-result/1`, JSON Schema — `tests/scenarios/schema/trace-result.schema.json`) используется и для правильного ответа, и для результата трассировщика. Суммы — строки с 6 знаками после точки, без чисел с плавающей точкой.

| Раздел | Что в нём | Ключ факта | Что сравнивается |
|---|---|---|---|
| `transfers` | переводы, по которым шли отслеживаемые средства | `transfer:<сеть>:<txid>:<event_index>` | отправитель, получатель, сумма, актив; `taint` (`traced` — точно украденные, `uncertain` — после смешения, `none` — контекст); `verification` (подтверждено вторым источником или нет) |
| `routes` | маршруты: последовательность TXID от кражи и конечная точка (адрес и причина остановки); `kind`: основной или боковая ветка | маршрут — TXID и адрес конца; остановка — `stop:<сеть>:<адрес>:<последний txid>` | найден ли маршрут; причина остановки |
| `exchange_deposits` | депозитный адрес, биржа, горячий кошелёк, TXID свипов | `exchange_deposit:<сеть>:<адрес>` | биржа, горячий кошелёк, свипы |
| `bridge_exits` | TXID выхода, протокол, dstEid, поддерживается ли, получатель, суммы, guid, TXID на стороне назначения | `bridge_exit:<сеть>:<txid>` | все поля, которые наблюдаемы |
| `merges` | адрес смешения, входы украденных средств, отметка «происхождение не определено» | `merge:<сеть>:<адрес>` | `attribution` и входы |
| `limitations` | ограничения источников: недоступен, список неполный, пробел в данных | `limitation:<роль источника>:<адрес / txid / *>` | вид ограничения |

Только в правильном ответе:
- `allowed` — верные факты, которые сообщать можно, но не обязательно: переводы глубже заданной глубины, выводы после смешения (с `taint: uncertain`), свипы бирж;
- `traps` — ловушки: входящие платежи жертве до кражи, нулевые переводы отравления, пыль с похожих адресов, неуспешные транзакции, Approval, чужие средства, внутренние операции биржи;
- `outages` — заложенные отказы источников и пробелы в индексе;
- `evidence_boundaries` — производный список: где кончаются доказательства (неподдерживаемый мост, неподтверждённое назначение, отказ источника, неполный список, пробел в данных, предел глубины);
- `meta` — категория, вариант, описание;
- у факта поле `excluded`: `source_unavailable` или `source_data_gap` — факт за заложенным отказом, в знаменатель не входит.

Причины остановки маршрута: `funds_at_rest`, `exchange_deposit`, `exchange_hot_wallet`, `known_service`, `bridge_exit_supported`, `bridge_exit_unsupported`, `bridge_destination_unconfirmed`, `commingled`, `max_depth`, `source_unavailable`, `incomplete_listing`, `data_gap`.

## Правила подсчёта

Правила владельцев (раздел 1.5):
1. Точность фактов считается по каждому факту.
2. Сценарий трассировки засчитан, если найдены все ожидаемые маршруты и нет ни одного ложного факта.
3. Недоступность источника исключается из знаменателя, но считается и выводится отдельно.
4. Итоговая оценка — на отложенном наборе; case-001 в него не входит.

Как это реализовано в оценщике (`src/ledgerhunt/scenarios/scorer.py`):

| Исход факта | Когда | В знаменателе |
|---|---|---|
| верный | найден, все сравниваемые поля совпали | да |
| слабее | найден и верен, но менее конкретен: `uncertain` вместо `traced`, «не подтверждено» вместо «подтверждено», не все свипы | да, но не засчитан как верный и не ложный |
| пропущен | ожидаемый факт не найден | да |
| ложный | противоречит ответу или данным: неверная сумма или стороны, несуществующий перевод, неуспешная транзакция, нулевой перевод или ловушка как движение средств, точное происхождение после смешения, «подтверждено» при недоступном втором источнике, биржа или мост там, где их нет, отказ источника, которого не было, неверная причина остановки | да; один такой факт проваливает сценарий |
| нейтральный | верный, но не обязательный (`allowed`, контекстные переводы с `taint: none`) | нет |
| исключён | факт за заложенным отказом источника или пробелом в индексе | нет, считается отдельной строкой |

- Маршрут найден, если в результате есть маршрут с теми же TXID и тем же концом или маршрут, который начинается с ожидаемых TXID и идёт дальше. Продолжение за точкой остановки оценивается по фактам, которые при этом заявлены.
- Полнота фактов = верные / ожидаемые в знаменателе. Точность фактов = (верные + слабее) / (верные + слабее + ложные).
- Доля засчитанных сценариев = засчитанные / сценарии без заложенного отказа источника; публикуется с 95% интервалом Уилсона (например, 50 из 50 дают нижнюю границу 92.9%).
- Сценарии с заложенным отказом (в наборе для разработки их 9: 6 из source_failure и 3 из incomplete_data — пропущенные страницы и пробел в индексе) в знаменатель не входят и выводятся отдельно: сколько их и сколько обработано правильно (все ожидаемые маршруты до границы, ни одного ложного факта; сообщение об ограничении — ожидаемый факт).
- Для будущих сценариев в реальной сети, где отказы не заложены заранее, есть режим `--trust-candidate-outages`: отказы, заявленные трассировщиком, исключают зависящие от них факты. В синтетических наборах он выключен, иначе заявление об отказе позволяло бы уменьшать знаменатель.

Проверка самого оценщика на всём наборе для разработки (прогон в `results/stage-2/scenarios/`): правильный ответ как результат — засчитано 45 из 45, полнота 1.0, ложных 0, 9 сценариев с отказами обработаны; пустой результат — засчитано 0; правильный ответ плюс один выдуманный перевод — засчитано 0 из 45, ложных фактов 54 (по одному на сценарий). Модульные тесты проверяют те же правила на отдельных сценариях: выдуманный факт, неверная сумма, пропущенный маршрут, точное происхождение после смешения, ловушка как движение средств, ложное заявление об отказе, «подтверждено» без второго источника, исключение из знаменателя.

## Отложенный набор и его защита

- 27 сценариев, по 3 на категорию, создан один раз из отдельного случайного seed (`tests/scenarios/holdout/seed.txt`; в манифесте только его sha256).
- **Набор не хранится в git.** В репозитории остаются только `tests/scenarios/holdout/README.md` и `manifest.json` с хешами; сценарии `hold-*/` и `seed.txt` исключены `.gitignore` и передаются владельцам архивом `handover/holdout-2026-10-14.zip` (папка `handover/` тоже не в git). Без содержимого набора проверки не падают: прогон раздела и `verify-holdout` пишут «отложенный набор у владельцев, проверка по манифесту пропущена», тест целостности в pytest пропускается. Как проверить копию из архива по манифесту — в `tests/scenarios/holdout/README.md`.
- `tests/scenarios/holdout/README.md` запрещает использовать набор при разработке и настройке.
- `manifest.json` хранит sha256 каждого файла и общий `tree_sha256`; карты «идентификатор → категория» в нём нет.
- Обычный прогон никогда не перезаписывает отложенный набор. Если набор есть на диске, прогон проверяет хеши (совпали 1695 из 1695 файлов сценариев), заново генерирует набор во временный каталог и сравнивает хеши (результат — «identical»), выполняет структурную проверку и выводит только количества.
- Оценщик отказывается оценивать отложенный набор без флага `--owner-final-evaluation`; модульные тесты читают из него только хеши.
- Ограничение: генератор и шаблоны лежат в репозитории, поэтому отложенный набор защищает от подгонки под конкретные экземпляры (адреса, суммы, порядок, TXID), но не под семейство шаблонов. Для независимой итоговой оценки владельцам стоит после заморозки кода добавить сценарии, составленные другим человеком или другой версией генератора, и сценарии на собственных переводах в основной сети. Набор уже вынесен из git (оставлен только `manifest.json`); владельцы могут создать и собственный закрытый: `python -m ledgerhunt.scenarios create-holdout --seed <значение> --out <каталог вне репозитория>`.

## Сценарии в реальной сети: что ещё нужно и сколько стоит

Синтетика проверяет логику трассировки, но не проверяет: реальные задержки и полноту источников, свежесть индекса, настоящие ошибки провайдеров, поведение настоящих бирж и мостов. По предложению Этапа 1 в «не менее 50» засчитываются синтетические сценарии и сценарии на собственных переводах в основной сети. Для вторых нужны средства владельцев; ниже — расчёт, не замер.

Опорные значения, измеренные по сырым ответам case-001 (2026-09-21, `data/http-store`):
- перевод USDT на адрес с нулевым балансом USDT: 130 285 энергии (транзакция `98f3ffca…`), плата за пропускную способность 0.345 TRX;
- цена энергии при сжигании TRX: 100 sun за единицу (транзакция `b49b0157…`: 22 267 900 sun за 222 679 энергии);
- отправка USDT0 в Ethereum: комиссия сети 23.0039 TRX, плата LayerZero 5.887806 TRX (call_value), комиссия USDT0 0.03% суммы (3.871584 USDT с 12 905.28).

Отсюда один перевод USDT на новый адрес при сжигании TRX ≈ 13.37 TRX. Перевод на адрес, где уже есть USDT, дешевле — не измерено. Активация нового адреса (1 TRX по документации TRON) — не проверено замером. Аренда энергии может быть дешевле сжигания — не измерено.

| № | Сценарий в сети | Переводов USDT | Прочее | Расчёт, TRX |
|---|---|---|---|---|
| R1 | прямой перевод | 1 | — | ≈ 13.4 |
| R2 | цепочка из 10 переходов | 10 | — | ≈ 134 |
| R3 | разветвление на 3 + 1% | 4 | — | ≈ 53 |
| R4 | слияние с «чужими» (своими же) средствами | 3 | — | ≈ 40 |
| R5 | цикл A→B→C→A→D | 4 | — | ≤ 53 |
| R6 | нулевой перевод между своими адресами | 1 (0 USDT) | — | ≤ 13.4, не измерено |
| R7 | неуспешная транзакция (малый fee_limit) | — | сгорает fee_limit, задаём сами, например 5 TRX | ≈ 5 |
| R8 | депозит на свою биржу и свип | 1–2 | аккаунт на бирже с верификацией | ≈ 13–27 |
| R9 | мост USDT0 в Ethereum | 1 approve + отправка | 0.03% суммы | ≈ 29 + approve (не измерено) |

Итого по расчёту около 380–400 TRX вместе с активацией примерно 25 новых адресов, плюс оборотные 50–100 USDT (они возвращаются, кроме 0.03% на мосту) и аккаунт на бирже. Перевод в доллары — не измерено: нужен курс TRX на дату покупки. Обратный путь из Ethereum (газ в ETH, Rango или NEAR Intents) — не измерено. Сценарии отказов источников (R10) в сети не нужны: они проверяются на записанных ответах.

## Что дальше

- После постройки трассировщика: прогнать его на наборе для разработки через `score`, затем на case-001; отложенный набор — только при итоговой оценке у владельцев.
- Базовый алгоритм без AI (эталонный прогон case-001, [case-001-reference-run.md](case-001-reference-run.md)) на 54 сценариях для разработки не прогонялся, поэтому его доли засчитанных сценариев пока нет. Это исходная точка для сравнения AI с базовым алгоритмом (Промпт 3); её нужно получить тем же `score` на наборе для разработки. Совпадение базового алгоритма с эталоном case-001 получено на тех же данных, по которым подбирались его пороги, и такой оценкой не является.
- Решение владельцев: делать ли сценарии R1–R9 в основной сети и выделить средства.
- Когда появятся реальные образцы ответов для неуспешных транзакций, Approval и ошибок провайдеров (их записывает раздел `tron_sources`), сверка форматов покажет, нужно ли поправить генератор.
- Если хранить сырые ответы набора в git нежелательно (около 14 MB и 4 700 файлов), их можно исключить: они пересобираются побайтно той же командой, а `manifest.json` доказывает совпадение.
