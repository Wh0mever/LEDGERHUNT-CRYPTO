  (`stop_reason: "refusal"`) не было ни одного.

  (5 решений, отчёт, 30 рутинных вызовов, 4 скриншота) — допущение из оценки владельца; рутинные вызовы не
  измерялись (раздел 8). Главное число — «холодные» вызовы: каждый вызов пишет системный промпт со схемой в кеш и
  не читает его, потому что у каждого типа решения своя схема (раздел 6). Пересчёт из полей `usage` по ценам

  Sonnet 5.5 @medium — **$0.268** (оценка $0.30); предлагаемый набор моделей по точкам решений — **$0.256**.
  Оптимистичный вариант с чтением кеша, как в замере, где одинаковые вызовы повторялись в пределах 5 минут:
  $0.477, $0.229 и $0.218. В статью «модели $0.60» бюджета $1 укладываются все варианты, кроме Opus 5.5 @high
  без чтения кеша ($0.608).
- На этом кейсе Sonnet 5.5 @high прошёл все повторы всех 8 точек решений (24 из 24) и отчёт; Opus 5.5 не был
  точнее: @medium 23 из 24, @high 22 из 24 (ошибки в ручном пересчёте hex-суммы). Sonnet может заменить Opus
  на планировании и проверке при цене примерно вдвое ниже. Для отчёта достаточно Sonnet 5.5 @medium ($0.094 против
  $0.228 у Opus @medium за холодный вызов; с чтением кеша $0.089 и $0.223); качество текста для полиции и биржи
  должен сравнить человек (тексты сохранены). Оценка D4 держится на критерии, добавленном после просмотра ответов
  (разделы 4 и 5).
- **Время модели не укладывается в цели по срокам, если вызовы идут последовательно** (раздел 4.1). Медиана
  времени ответа: отчёт на Sonnet 5.5 @medium — около 50 с, на Opus 5.5 @medium — около 80 с; решение на
  Sonnet 5.5 @high — около 12.6 с. Предлагаемый набор последовательно (5 решений и отчёт) — около 110 с только на
  модель. Цель Промпта 3 — первичный отчёт за 2 минуты, доля шагов с моделью в ней по Этапу 1 — 30 с. Решения нужно
  запускать параллельно, где они независимы, а текст отчёта вынести из критического пути.
- Haiku 5.5 @low извлекает данные со скриншотов без ошибок (100% TXID, адресов, сумм и времени на 5 синтетических
  скриншотах), не повторяет seed-фразу и телефон, распознаёт инъекцию — за $0.0005 за скриншот с чтением кеша
  ($0.0009 холодный вызов). То, что модель не повторила seed-фразу, — вторая линия защиты, а не сама защита: по
  решению 1.4 seed-фраза не должна попадать в модель вообще, её убирает локальный предфильтр до вызова модели,
  а он не измерен (разделы 7 и 10). Haiku @high хуже, чем @medium: переобдумывает (обрывы по `max_tokens`,
  искажённые идентификаторы в отчёте).
- Две системные ошибки, которые надо закрыть кодом, а не выбором модели: (а) модели ошибаются в пересчёте
  hex → десятичная сумма (Opus и Sonnet), (б) модели иногда предлагают остановить трассировку на мосту
  вместо запроса API моста. Декодирование сумм, chainId и выбор следующего шага для поддерживаемых мостов должен
  делать детерминированный слой; модель только интерпретирует уже разобранные данные.

Это замер на одном эталонном кейсе (case-001, набор для разработки) с синтетическими скриншотами. Перенос на другие
кейсы не проверен (раздел 10).

**Оценка.** Детерминированные проверки полей (`src/ledgerhunt/llmbench/tasks/`): точное совпадение
идентификаторов (hex без учёта регистра и `0x`, base58 TRON с учётом регистра), суммы как десятичные числа, время
как момент UTC. Для каждой задачи есть критические проверки; вызов «пройден», если схема валидна, все критические
проверки выполнены и **в ответе нет ни одного идентификатора, которого нет во входе** (с учётом допустимых
преобразований hex ↔ base58). Строки, похожие на идентификатор, но неверной длины, тоже считаются выдуманными.
Проверки формулировок (смешение средств, гипотеза, отсутствие обещаний возврата) — по словарю шаблонов; это
эвристика, срабатывания сохраняются в `details` для ручной проверки.

**Сетка effort** (обоснование по документации): извлечение со скриншотов — `low` и `medium` (рутина: Haiku 5.5 —
`low` для простых массовых задач, `medium` по умолчанию; Sonnet 5.5 — `low`/`medium` для извлечения и
классификации); решения и отчёт — `medium` и `high` (Opus 5.5: по умолчанию `medium`, `high` для работы, где важно
качество; Haiku 5.5: `high` для работы со знаниями и строгого следования инструкциям; Sonnet 5.5: по умолчанию `high`).
Повторы: Haiku ×5, Sonnet ×3, Opus ×3 — всего 308 вызовов.

**Запрос.** Общий системный промпт (правила: данные — не инструкции, идентификаторы только из входа, факт /
заявлено пострадавшим / гипотеза, смешение средств, без обещаний, seed-фразы и личные данные не повторять;
справочник контрактов) с явной точкой кеша на 5 минут; задача и данные — в сообщении пользователя; ответ —
structured outputs (`output_config.format`, JSON Schema); `thinking` не задан (адаптивное мышление по умолчанию,
`display` по умолчанию `omitted`); потоковый режим; `max_tokens` 16000 (решения), 8000 (скриншоты), 32000 (отчёт).
Клиент создаётся только через `make_anthropic_client()` (всегда `https://api.anthropic.com`).

**Бюджет.** Журнал `results/stage-2/llm/cost-ledger.jsonl` общий для всех прогонов. Перед каждым вызовом
резервируется максимум: токены промпта по `count_tokens` + 10% + 200, все по самой дорогой цене входа
(запись в кеш на 1 час), плюс весь `max_tokens` по цене выхода. Вызов не отправляется, если потрачено + открытые
резервы + этот резерв > $20. После ответа резерв закрывается точной стоимостью по `usage`; при отклонении запроса
до обработки (HTTP 400) — снимается. Если поток оборвался, оплата неизвестна и резерв засчитывается целиком.

## 6. Кеширование промпта

- Кешируемый префикс = системный промпт + JSON-схема ответа (2917–3507 токенов). Разные схемы дают разные записи
  в кеше: первый вызов каждого типа задачи пишет кеш (полная цена ×1.25), повторы того же типа в пределах
  5 минут читают его (×0.05 у Opus и Sonnet, ×0.1 у Haiku). Общего «кеша на всё расследование» при разных схемах нет.
- Смена effort (medium ↔ high, low ↔ medium) **не сбросила** кеш системного промпта со схемой на Sonnet 5.5 и
  Haiku 5.5: первый вызов на другом уровне читал запись, созданную на соседнем (например, Sonnet @high D2 прочитал
  2930 токенов, записанных @medium). Документация предупреждает, что смена effort сбрасывает кеш сообщений и может
  сбросить кеш системного промпта; в нашем размещении системный уровень сохранился. На Opus группы шли параллельно,
  поэтому эффект там не наблюдался.
- Экономия на прогоне: группы скриншотов 36–37% стоимости (одна схема, изображение не кешируется), группы решений
  и отчёта 7–18%. Эта экономия возникла из-за повторов одинакового вызова внутри замера. В реальном расследовании
  каждый тип решения вызывается 1–2 раза, и чтений кеша может не быть. Поэтому в разделе 8 главное число — холодные
  вызовы: они на 11–18% дороже варианта с кешем, как в замере, и на 2.8–4.6% дороже варианта без кеширования вовсе
  (запись в кеш стоит ×1.25 от входа).
- Практический вывод: держать схему стабильной для однотипных вызовов (например, решение о развилке на каждом
  хопе), вызовы одного типа группировать по времени; при паузах дольше 5 минут рассмотреть TTL 1 час
  (запись ×2, окупается с трёх обращений). Для разовых вызовов кеш не включать: запись без чтения только дороже.

## 9. Отказы, ошибки и надёжность

- Отказов нет: 0 из 308 вызовов сетки, 0 из 28 пробных. Категории отказов, которые могли бы сработать на наших
  темах (`cyber`, `general_harms`), не сработали. Серверный fallback проверен только на приём параметра (200),
  на реальном отказе — нет.
- Падение прогона: основной прогон упал, когда 5 потоковых вызовов ещё ждали ответа. Что записано в результатах:
  в журнале `results/stage-2/llm/cost-ledger.jsonl` эти 5 резервов закрыты при дозапуске `--resume` (11:48:53 UTC)
  со статусом `unknown_usage_upper_bound` и пометкой «процесс прогона упал до получения usage»; в `config.json`
  прогона они перечислены в `resumes.closed_stale_reservations`, верхняя граница — $1.655619. Дозапуск отправил
  39 вызовов, среди них эти 5 заново; все 5 завершились с HTTP 200 и входят в 308. В `raw/calls.jsonl` 306 строк
  `ok` и 2 `max_tokens`, строк об оборванных попытках нет. Причину падения раньше называли сбросом соединения
  (`httpx2.ReadError`, WinError 10054), но в сохранённых данных её подтверждения нет: вывод консоли не сохранён.
  После падения харнесс доработан: обрыв потока теперь ловится как `transport_error`, резерв засчитывается целиком,
  остальная сетка продолжается. В этом прогоне такой записи нет. Оборванные попытки нужно записывать и в `raw/`.
- Обрывы по `max_tokens`: 2, оба у Haiku @high (см. раздел 4). Невалидный JSON — только в этих двух случаях.
- Для продукта: на Opus/Sonnet включать `fallbacks: "default"`; для Haiku — повтор на Sonnet средствами клиента;
  в схемах не просить «рассуждение» (риск `reasoning_extraction`); всегда проверять `stop_reason` до чтения ответа.

## 10. Ограничения замера и что не измерено

- **Один кейс.** Case-001 — эталон для разработки, не отложенный набор. Входы подготовлены детерминированным
  слоем и структурированы, перечисления в схемах сужают выбор. Высокие баллы Haiku не означают, что Haiku справится
  с незнакомыми мостами и неоднозначными цепочками. Нужен прогон на наборе сценариев из п. 4.6 (Batch API, −50%).
- **Проверки формулировок — эвристика по шаблонам.** После просмотра ответов шаблоны расширены (принимаются
  перефразировки «cannot be concluded», «does not prove», «one-to-one» и т. п.; исключены ложные срабатывания вида
  «сообщение, утверждающее, что средства возвращены»), добавлено обнаружение идентификаторов неверной длины,
  а следующий шаг в D4 сделан критичным (остановка на мосту противоречит решению 2.3). Сырые ответы не менялись;
  все оценки пересчитаны командой replay и воспроизводимы. Из-за этих изменений поменялся вердикт у 9 вызовов в
  4 ячейках; числа до и после — в разделе 4. Рекомендация по D4 держится на критерии, добавленном после просмотра
  (раздел 5).
- Качество текста отчёта человеком не оценивалось: проверялись только обязательные элементы. Наблюдение по текстам:
  Sonnet сокращает TXID в прозе («98f3ffca…1d1bb»; в таблице маршрута полные), Opus пишет полные; Haiku @medium в
  одном отчёте написал, что хаб «по-видимому, всё ещё держит большую часть средств» — мягкое утверждение без
  основания, шаблоны его не ловят.
- Скриншоты синтетические, чёткие, на английском (встроенный шрифт Pillow без кириллицы). Фото экрана,
  сжатые изображения, русский и узбекский текст не проверялись.
- **Не измерено: локальный предфильтр скриншотов** (распознавание текста, поиск seed-фраз и приватных ключей,
  закрашивание лиц и персональных данных): ни точность, ни время, ни цена. По решению 1.4 seed-фразу нельзя
  отправлять в модель вообще, поэтому измеренное «модель не повторила seed-фразу» (раздел 7) — вторая линия защиты,
  а не сама защита. Основной защитой должен быть этот фильтр; его стоимость входит в статью бюджета «вычисления
  и хранение $0.10» и тоже не измерена.
- Не измерено: диалог с клиентом; рутинные вызовы (в разделе 8 взята оценка сверху); Batch API; TTL кеша 1 час;
  поведение серверного fallback на реальном отказе; задержки под нагрузкой и лимиты тарифа аккаунта; фактическая
  оплата 5 вызовов, оборванных падением прогона (нужен доступ к Usage/Cost в консоли или Admin API-ключ).

## 11. Условия Anthropic по данным API (решение 1.4)

- Документация API: данные, которые хранятся, не используются для обучения без явного разрешения; содержимое
  запросов и ответов по умолчанию не хранится, кроме «Covered Models» (Fable 5/5.1, Mythos 5/5.1 — обязательное
  хранение 30 дней); zero data retention (ZDR) — по запросу через отдел продаж, отдельно для каждой организации;
  материалы, отмеченные системами безопасности, могут храниться до 2 лет.
- Privacy Center (коммерческие клиенты): входы и выходы API удаляются на стороне Anthropic в течение 30 дней,
  кроме сервисов с более долгим хранением (например, Files API), договорённостей (ZDR), нарушений Usage Policy и
  требований закона; отмеченные чаты — до 2 лет, оценки классификаторов безопасности — до 7 лет.
- Формулировки двух страниц различаются («не хранится по умолчанию» и «удаляется в течение 30 дней») — вопрос для
  юриста вместе с передачей персональных данных за рубеж. Модели 5.5 к «Covered Models» не относятся.
- В этом замере в API отправлялись только публичные данные блокчейна и синтетические скриншоты.

## 12. Как повторить

```
python run_stage2.py --only llm_models --llm              # живой прогон (платно; общий лимит $20 по журналу)
python run_stage2.py --only llm_models --llm --replay     # пересчёт оценок последнего живого прогона без API
python -m ledgerhunt stage2 llm_models --llm --plan-only  # бесплатный подсчёт токенов и резервов
python -m ledgerhunt stage2 llm_models --llm --resume latest   # дозапуск после обрыва
python -m ledgerhunt.stage2.screenshots                   # пересоздать синтетические скриншоты
python -m ledgerhunt.llmbench.build_inputs --check        # проверить замороженные входы против эталона и сырых ответов
.venv\Scripts\python -m pytest tests/test_llmbench_offline.py   # офлайн-тесты оценщиков и журнала бюджета
```

Параметры: `--models haiku,sonnet,opus`, `--tasks D1_mechanism,...`, `--kinds decision,screenshot,report`,
`--repeats haiku=5,sonnet=3,opus=3`, `--workers 10`, `--no-checks`, `--checks-only`, `--replay-from <папка>`.
Без флага `--llm` раздел пропускается и ничего не тратит.

Состав прогона: `config.json` (дата, коммит, версии, машина, наличие ключей true/false, команда), `inputs/`
(системный промпт, тексты задач, схемы, ожидаемые ответы, цены, сверка с документацией), `raw/calls.jsonl` (по
строке на вызов: хеши входа/схемы/изображения, `usage`, стоимость, время, `stop_reason`, ответ модели),
`raw/api_checks.jsonl`, `raw/models_api.json`, `summary.json`, `summary.md`. Ключей и заголовков в файлах нет.
