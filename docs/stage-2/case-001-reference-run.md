## 4. Эталонный прогон: как работает

Код: пакет `src/ledgerhunt/baseline/` (без AI, без сети при `--replay`). Вход — только TXID кражи, реестр известных мостов и меток с источниками ([registry.py](../../src/ledgerhunt/baseline/registry.py)) и пороги. Адреса из эталона в коде не прописаны; адреса в реестре — это контракты мостов и один размеченный горячий кошелёк биржи.

Правила:

1. **Старт.** Разобрать транзакцию и квитанцию. Перевод токена от подписанта — это кража. Механизм: число подписей, Permission_id, подписант, восстановленный из подписи, права жертвы и изменения прав в её истории. Контекст: входящий платёж до кражи, ресурсы, полученные за 120 с до неё, другие исходящие жертвы в окне ±120 с.
2. **Следование за деньгами.** Пусть на адрес H пришла сумма A в момент T. Исходящие USDT адреса H после T берутся по времени, пока их сумма не достигнет A × (1 − 0.001); переводы в той же секунде добавляются. Каждый взятый перевод классифицируется:
   - не меньше 20% от A — ветка, по ней идём дальше;
   - ровно 1% от A с точностью токена (вниз или по правилам округления) — «точный процент»;
   - не больше 1 USDT — пыль;
   - всё остальное — боковая ветка.

   Невзятое считается остатком на адресе. Пыль в течение часа после основного вывода отмечается как остаток.
3. **Мосты.**
   - Событие OFTSent в квитанции. Дальше LayerZero Scan даёт транзакцию назначения, а OFTReceived в Ethereum — получателя и сумму. Вторым источником служит квитанция публичного RPC.
   - Событие RangoBridgeInitiated: сумма моста, destinationChainId, ASCII-получатель; переводы из Diamond дают комиссию партнёра и пересылку.
   - Адрес, который узнаёт API NEAR Intents 1Click: получатель, транзакция назначения и выплата на TRON.

   В другой сети читается только участок моста.
4. **Хаб (стоп).** За 24 ч после поступления у адреса не меньше 10 разных контрагентов или прочий объём USDT не меньше 5 × A. Хаб в TRON с USDT-TRC20 становится кандидатом на заморозку с пометкой «средства смешаны».
5. **Выход на биржу.** Проверяются выходы хаба за 24 ч, не больше 10. Получатель считается депозитным адресом, если за 1 ч переслал не меньше 99% полученного на один адрес и у него не больше 3 контрагентов в окне 6 ч. Это выход на биржу, если адрес назначения есть среди размеченных горячих кошельков. Метка — входные данные с указанным источником.
6. **Общий источник TRX.** Источник — это отправитель активирующего перевода или переводов от 1 TRX, полученных адресом среди первых 50 входящих. Учитываются источники, которые финансировали не меньше 2 адресов со стороны вора и не финансировали жертву. Балл: +1 (≥2 адресов), +1 (≥3), +1 (финансирование по обе стороны моста), −1 (у источника больше 50 разных получателей TRX среди первых 200 исходящих транзакций — похоже на сервис пополнения). Уровни: 1 — low, 2 — medium, 3 — medium-high, 4 — high. Это вывод «вероятно один оператор», а не факт.

## 8. Отклонения от плана и исправления в ходе работы

- В первом живом прогоне (`20261014T113111Z`) шаг 2 содержал две ошибки моего кода. Проверка баланса жертвы ошибочно применилась к плательщику TBY9jt…, потому что в его роли есть слово «victim». Активация TYGdh7 сверялась с `create_time` (11:35:24) вместо времени активирующего перевода (11:35:27). Обе ошибки исправлены, основной замер — второй прогон. Сырые ответы первого прогона остались в хранилище и описи.
- Правило «точный процент» сначала признавало только округление вниз. Сверка повторного маршрута 30.08 показала, что сервис округляет и по правилам округления (30.892644). Правило расширено на оба варианта, для case-001 результат не изменился.
- Ключ TronGrid при работе уже был задан, хотя в отчёте фундамента было написано «нет ключа». Поэтому все замеры TronGrid здесь сделаны с ключом. Замер без ключа здесь не делался.
- Сверх задания добавлена одна проверка метки на Etherscan (ключ есть) для «explorer tag»: эндпоинт оказался платным.

## 9. Ограничения и что нужно

- **Второй источник для TRON.** Бесплатный PublicNode не хранит историю: `{}` по всем 45 транзакциям 21–22.09 и раньше. Поэтому факты TRON подтверждены одним провайдером, TronGrid, но двумя его подсистемами (API узла и индекс v1), и они везде согласны. Для двух транзакций мостов есть независимые подтверждения: LayerZero Scan для b49b0157… и 1Click для d3cd82b7…. Чтобы получить настоящий второй источник, нужен платный архивный RPC TRON (`TRON_RPC_URL`). Перевыгрузка подхватит его автоматически.
- **Ethereum.** Бесплатный PublicNode не отдаёт `eth_getLogs` по старым блокам (403, нужен токен). `eth_getTransactionReceipt` иногда возвращает `result: null` по известной транзакции: в хранилище 3 из 11 вызовов, все по 0x41bac…. Код делает один повтор через 2 с и помечает недостающий второй источник. Для работы без пропусков нужен `ETH_RPC_URL`. Офлайн-повтор шага 2 даёт 245 / 3 / 23, а живой прогон — 244 / 3 / 24. Причина в том, что при повторе берётся последний записанный ответ на тот же запрос. Для квитанции 0x41bac… это ответ с данными, который пришёл в шаге 3 живого прогона через минуту после двух `null`.
- **Метки бирж и обозревателей.** TronScan без ключа отвечает 401. Метки Etherscan есть только на тарифе API Pro. Без них выход на WhiteBIT держится на входной метке из ручного расследования. Сама схема «депозитный адрес → горячий кошелёк» подтверждена TXID.
- **Тест по эталону.** `tests/test_case001_replay.py` прогоняет эталонный алгоритм офлайн из записанных ответов (сеть запрещена на уровне транспорта) и сравнивает смысловую часть результата с `tests/fixtures/case-001/raw/expected/reference-run.json`. Хэши тел, живые балансы и время в сравнение не входят. Живой прогон и офлайн-повтор дали одинаковый результат.

## 10. Как повторить

```
python -m ledgerhunt stage2 case001            # живой прогон: шаги 1–4, запись в tests/fixtures/case-001/raw/
python -m ledgerhunt stage2 case001 --replay   # офлайн, из записанных ответов
python -m ledgerhunt stage2 case001 --replay --update-expected   # переписать ожидаемый результат
python -m pytest tests/test_case001_replay.py
```

Аналоги через `run_stage2.py`: `python run_stage2.py --only case001 [--replay]`. Каждый живой прогон дописывает в хранилище фикстуры около 340 ответов и обновляет MANIFEST.md; после него нужно обновить списки ответов, которые не попадают в git: `python -m ledgerhunt.core.restricted` (раздел 2). Запросы к TronScan и Etherscan повторно не отправляются: их ответы берутся из записи.

Файлы: код — `src/ledgerhunt/baseline/`, `src/ledgerhunt/stage2/case001.py`, `src/ledgerhunt/sources/case001_tronscan.py`, `src/ledgerhunt/sources/case001_etherscan.py`; сырые ответы и опись — `tests/fixtures/case-001/raw/`; результаты — `results/stage-2/case-001/`.
