Дата замеров: 2026-10-14 (UTC). Машина: Windows 11 Pro, Intel i9-13900H (14 ядер / 20 потоков), 31,6 ГБ ОЗУ, Python 3.13.0. Коммит при замере: `90bd06b` (рабочее дерево с незакоммиченными файлами Этапа 2).

Прогоны с записью: [20261014T114433Z](../../results/stage-2/bridges/20261014T114433Z/) (11:44–11:50 UTC) и [20261014T120105Z](../../results/stage-2/bridges/20261014T120105Z/) (12:01–12:06 UTC), по 442 HTTP-запроса, около 5,5 мин каждый. Офлайн-повтор без сети: [20261014T120636Z](../../results/stage-2/bridges/20261014T120636Z/) (раздел 11).

Ключи, которые были в `.env` во время прогонов (записано только наличие): TronGrid — есть, Etherscan — есть, Anthropic — есть (здесь не используется). Нет: платного Ethereum RPC, Blockscout PRO, ключа партнёра NEAR Intents, ключа Rango.

## 1. Коротко

1. Все три моста case-001 распознаются и проходятся по сырым данным. Сверка фактов мостов из эталона (шаги 12, 14–17): 54 факта, все совпали. Два различия в смысле полей 1Click описаны в разделе 8 и в эталоне не являются ошибкой. Вне этих 54 фактов у эталона есть одно расхождение, которое касается моста: транзитный адрес 0x4079…926d работал не с августа («reused Aug–Oct 2026»), а как минимум с 2026-06-04. Это расхождение фактов №3 в [case-001-reference-run.md](case-001-reference-run.md), раздел 3.2 (подробности — раздел 14).
2. Выборка шире case-001: транзитный адрес 0x4079…926d получил 6 переводов USDT0 из TRON и сделал 8 отправок через Rango. Все 14 участков пройдены до получателя: в 6 из 6 случаев USDT0 получатель и транзакция назначения совпали на двух независимых путях; в 8 из 8 случаев Rango выплата в TRON найдена и совпала с получателем.
3. **LayerZero Scan не годится как основной источник для продукта.** Условия использования разрешают только личное некоммерческое использование и запрещают автоматический доступ и хранение данных. Получателя и транзакцию назначения USDT0 мы нашли без LayerZero Scan, только по цепочке: событие `OFTSent` в TRON → `OFTReceived(guid)` в Ethereum через `eth_getLogs`. Совпадение — 6 из 6. В продукте LayerZero Scan заменён этим разбором (раздел 10); в замерах Этапа 2 он использовался для сверки (60 HTTP-запросов в двух прогонах раздела).
4. **Получатель Rango в событии неполный.** `RangoBridgeInitiated.receiver` содержит только первые 20 символов TRON-адреса (например, `TYHeH2HQn7pM5fe6aYwG`). Полный адрес даёт мост на другой стороне: 1Click или USDT0. Без 1Click выплату можно найти в TRON по префиксу или по сумме среди переводов кошелька выплат NEAR Intents: 6 из 6 уникальных совпадений.
5. **Сумма `amountOut` в 1Click не равна фактической выплате.** В 6 из 6 USDT-выплат фактическая выплата больше на 0,042558–0,080423 USDT. Фактом считается только сумма из блокчейна.
6. **PublicNode Ethereum не годится как единственный источник.** В каждом из двух прогонов 4 из 21 квитанции пришли как `result: null` при HTTP 200 для существующих транзакций; за день так пришли 17 из 107 записанных ответов. Среди них обе транзакции Ethereum из case-001 (`0x8ea2…` и `0x41bac…`). Это ложное «не найдено». Исторический `eth_getLogs` на PublicNode без ключа запрещён (403).
7. **Blockscout `/token-transfers` неполон для спам-токенов.** Он пропустил 35 переводов двух токенов с репутацией `scam`. Логи Blockscout при этом совпали с квитанциями. Для фактов используем логи, а не список переводов.
8. Нет ключей, поэтому не измерены: платный Ethereum RPC, Blockscout PRO, статус 1Click с ключом партнёра, статус Rango (раздел 13). Etherscan v2 измерен с ключом бесплатного тарифа. Этот тариф по условиям Etherscan только для личного и исследовательского использования; коммерческое использование начинается с тарифа Advanced за $299 в месяц. Бесплатный ключ использовался только для исследования Этапа 2; в продукт Etherscan не берём (раздел 10).
9. **Рекомендация для продукта** (раздел 10): основной источник Ethereum для участков мостов — платный архивный Ethereum RPC в том же аккаунте Chainstack, что и узел TRON (ещё не измерен); второй источник — Blockscout PRO; LayerZero Scan заменён разбором `OFTSent`/`OFTReceived` из блокчейна; для 1Click — ключ партнёра и хранение ответов не дольше 24 часов.

## 3. Источники Ethereum и мостов: доступность и задержка

Два прогона с записью: 11:44–11:50 и 12:01–12:06 UTC. «Вызов» — логический запрос с проверкой смысла ответа: квитанция не `null`, хэш совпал, сообщение найдено. Задержка — последняя попытка HTTP; p50, p95 и max посчитаны по всем HTTP-запросам обоих прогонов, включая проверку кандидатов P1. Все запросы, кроме Etherscan и TronGrid, сделаны без ключа.

|---|---|---|---|---|---|---|---|
| Blockscout API v2 + Etherscan-совместимый API (eth.blockscout.com) | 99 / 99 | 97 / 99 | 300 | 10 | 285 | 2228 | 4267 |
| PublicNode Ethereum RPC | 58 / 58 | 53 / 54 | 124 | 0 | 128 | 278 | 457 |
| dRPC (eth.drpc.org) | 47 / 47 | 47 / 47 | 100 | 0 | 149 | 279 | 370 |

Отрицательные проверки (ожидаемый ответ 404: LayerZero Scan по транзакции Rango, 1Click по адресу 0x4079) в «успешные вызовы» не входят и в обоих прогонах дали 404.

Пояснения:
- Все неудачи PublicNode — ответ `{"result": null}` с HTTP 200 на `eth_getTransactionReceipt` для транзакций, которые остальные источники отдали. Прогон 1: в P3 `0x5536808a…`, `0x294c9434…`, `0xd4976262…` и транзакция Rango из case-001 `0x41bac088…`, плюс одна в серии P6. Прогон 2: в P3 `0x50d4ecef…`, `0x8ea2bdef…` (вход USDT0 из case-001), `0x41bac088…`, `0x98d966b8…`; серия P6 во втором прогоне шла через `eth_getTransactionByHash`, и все 20 ответов пришли. За 2026-10-14 в хранилище записано 107 ответов PublicNode на `eth_getTransactionReceipt` (все прогоны раздела, включая отладочные), из них 17 пустых. Одна и та же транзакция в разное время приходила то пустой, то полной: например, `0x41bac088…` — полная в 11:28, пустая в 11:47, снова полная в 11:49 UTC. Пустой ответ непостоянен и с возрастом транзакции не связан: пустыми приходили и транзакции июня, и транзакции 21 сентября.
- Две неудачи Blockscout в прогоне 1 — исчерпанная квота Etherscan-совместимого метода `/api?module=logs&action=getLogs`. У этого метода свой лимит: 10 запросов на календарный час. Заголовок `x-ratelimit-limit: 10`; сброс по `x-ratelimit-reset` в прогоне 1 приходился на 12:00:00 UTC, в прогоне 2 — на 13:00:00 UTC. После исчерпания сервер отвечает HTTP 429 с текстом «Too many requests. Increase limits now at https://dev.blockscout.com», повторы через 1–8 с не помогают. В прогоне 1 первый ответ уже показал остаток 3 из 10: шесть запросов этого часа сделал отладочный запуск раздела в 11:25–11:28 UTC. В прогоне 2, в новом часе, остаток шёл 9 → 4, все 6 запросов прошли. Методы API v2 (`/api/v2/…`) работают с другим лимитом: `x-ratelimit-limit: 180` на окно около 60 с, это около 3 запросов в секунду.
- Большие p95/max у Blockscout дают транзакции со спамом: сотни логов, до 17 страниц по 50 записей; на таких страницах ответ занимает 2–4 с. Для транзакций мостов (3–10 логов) 45 ответов Blockscout в прогоне 1 заняли от 0,19 до 0,77 с.
- LayerZero Scan и 1Click в каждом прогоне получили 29 и 27 вызовов в окне около минуты; прогоны разнесены на 17 минут. Выборки за сутки и в разное время дня не было, поэтому p95 этих двух API — оценка по 60 и 56 запросам.

## 7. Мосты case-001: как распознать выход, найти получателя и где граница доказательств

### 7.1 USDT0 / LayerZero (Legacy Mesh)

Контракты по официальному списку USDT0 (`docs.usdt0.to/api/deployments`, раздел Legacy Mesh, проверено в P0): TRON — `TFG4wBaDQ8sHWWP1ACeSGnoNR6RRzevLPt` (LayerZero eid 30420), Ethereum — `0x1F748c76dE468e9D11bd340fA9D5CBADf315dFB0` (eid 30101), Arbitrum — `0x77652D5aba086137b595875263FC200182919B92` (eid 30110).

а) Распознавание выхода в TRON. Транзакция вызывает контракт `TFG4wB…`; в сырых логах `gettransactioninfobyid` есть событие `OFTSent(guid, dstEid, fromAddress, amountSentLD, amountReceivedLD)` (topic0 `0x85496b76…`) и `PacketSent` эндпоинта LayerZero. Наш декодер читает из `PacketSent` заголовок пакета (nonce, srcEid, отправитель, dstEid, получатель-контракт, guid) и сообщение OFT. Наблюдаемый формат сообщения Legacy Mesh — 42 байта: `0x0002 | bytes32 sendTo | uint64 amountSD`. Смысл первых двух байт по исходному коду контракта не проверялся. Распознано 6 из 6.

б) Получатель и транзакция назначения:
- через LayerZero Scan: `/v1/messages/tx/{hash}` работает и по исходной, и по целевой транзакции, а также `/v1/messages/guid/{guid}`; в case-001 все три ответа совпали. Нужны guid, статус `DELIVERED`, целевая транзакция и `sendTo` из payload;
- без LayerZero Scan: guid из `OFTSent` → номер блока Ethereum по времени транзакции TRON (2–3 запроса `eth_getBlockByNumber`, якорный блок 26 000 000, шаг 12 с) → `eth_getLogs(address = OFT Ethereum, topics = [OFTReceived, guid])` в окне 150 блоков (около 30 мин) частями по 50 блоков → `toAddress`, сумма, хэш транзакции. Результат: dRPC 6/6, Tenderly 6/6, Etherscan v2 6/6 (каждому хватило одного запроса), Blockscout `/api` 4/6 (дважды исчерпана квота). Найденная транзакция совпала с LayerZero Scan в 6 из 6;
- суммы `amountReceivedLD` в `OFTSent` (TRON), `OFTReceived` (Ethereum), ERC-20 Transfer и `amountSD` в сообщении совпали в 6 из 6.

Расхождение одно: в таблице кандидатов P1 у PublicNode «квитанция» при записи — да, при повторе — нет. P1 и P3 отправляют одинаковый запрос квитанции `0x8ea2…`. Во втором прогоне P1 получил полную квитанцию, а P3 немного позже — пустую. Повтор отдаёт последний записанный ответ на одинаковый запрос, поэтому P1 при повторе видит пустой. Это ограничение повтора для непостоянных источников: повтор воспроизводит последний ответ на каждый уникальный запрос, а не каждую попытку.

## 15. Как повторить

```
python run_stage2.py --only bridges            # живой прогон с записью сырых ответов
python run_stage2.py --only bridges --replay   # офлайн-повтор из data/http-store
python -m ledgerhunt stage2 bridges --pace-s 5 --burst-n 20 --other-txs 6 --pool-cutoff 2026-10-14T00:00:00Z
```

Параметры по умолчанию записаны в `config.json` каждого прогона (`config.options`). Отсечка выборки `--pool-cutoff` фиксирует набор транзакций, поэтому новые переводы транзитного адреса не меняют замер.

Сырые ответы этого раздела занимают в `data/http-store/` около 29 МБ (839 уникальных тел, 1416 строк индекса с метками `bridges/…`). Из них 22,9 МБ приходится на ответы по транзакциям транзитного адреса, которые не относятся к мостам (спам и пыль; в выборку P3 последних прогонов вошли 6 из них, отладочный прогон брал больше). Больше всего весят страницы логов (8,1 МБ) и переводов (5,8 МБ) Blockscout у транзакций с сотнями логов. С `--other-txs 0` хранилище для нового прогона было бы в несколько раз меньше, но тогда в сравнении источников не будет транзакций с сотнями логов.
