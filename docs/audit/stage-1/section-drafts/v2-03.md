## 3. Готовые платформы и движки блокчейн-аналитики и трассировки

**Решение.** Готовую платформу или открытый движок за основу не берём: ядро — собственный детерминированный трассировщик (G8) поверх публичных API TRON (G5). GraphSense (MIT) — образец для изучения и кандидат на этап расширения на другие сети. Коммерческие платформы движком не служат: MistTrack даёт только точечные метки (G7), Arkham допускается для разовой сверки набора меток. Статус: принято; цели по времени и полноте условны до измерений Этапа 2.

### Почему выбрано
- Около 40 поисковых запросов по GitHub и чтение кода: зрелого открытого трассировщика TRC20 не найдено. Найдены краулер BlockchainSpider (MIT, 186 stars, без тестов и CI), консольный инструмент crypttrace (MIT, 20 stars), демо, хакатонные прототипы и два репозитория с признаками вредоносного кода. Перепроверка эти факты подтвердила.
- GraphSense v2.17.0 (2026-09-30) — единственная найденная зрелая открытая платформа с реальной загрузкой данных TRON, но на своём сервере ей нужны Cassandra, Spark, Delta Lake, PostgreSQL и полный узел TRON (README java-tron: минимум 8 cores / 32 GB / 3.5 TB). С сервером из G12 это несовместимо. Методик распределения смешанных средств в её коде нет.
- Коммерческие API не дают объяснимой трассы в бюджете $1: у MetaSleuth и Arkham нет эндпоинта трассировки; вызов MistTrack стоит $0.10–0.20 на пакетах до 10 000 вызовов (30 адресов = $3–6); Bitquery Coinpath (API потоков средств) есть только на плане Enterprise, и его алгоритм распределения сумм не документирован.
- «100% фактов с TXID» и воспроизводимость требуют полного контроля алгоритма: результат «чёрного ящика» в доказательном отчёте не объяснить.
- Живые пробы TronGrid 2026-10-13/14 (единичные запросы; под нагрузкой не измерялись): фильтры only_from, min_timestamp и order_by на /v1/accounts/{addr}/transactions/trc20 работают; /v1/transactions/{txid}/events отдаёт block_number и event_index; ответ за 0.39–0.66 с.

### Состояние проекта и расхождения «заявлено — на деле»
- Собственное ядро ещё не написано; оценка первичного исследования — 2–3 человеко-недели на ядро и тесты (не измерена).
- GraphSense: заявлен как полностью открытый, но поиск путей search_neighbors — закрытый сервис Iknaio; в открытых наборах меток (TagPacks) «currency: TRX» встречается в 6 файлах; 20 stars, два основных автора (1 231 и 795 коммитов, следующий — 59); есть 13 CI workflows и каталог tests.
- Iknaio: T&C опубликованы и ограничительны (см. выше); API отвечает — GraphSense API 2.17.0, 48 путей.
- Bitquery: вариант первичного исследования «Bitquery Pro за $69–99/мес для независимой сверки» перепроверкой снят — Coinpath есть только на Enterprise. Arkham: «tron» в списке сетей API есть, общий лимит — 100 запросов в секунду.
- TronGrid: 15 запросов в секунду в документации больше нет, опубликована только суточная квота; trc20-эндпоинт не отдаёт номер блока и индекс лога.

### Инфраструктура и затраты
- Постоянные: $0 в месяц за платформы и лицензии. Ядро — модуль на Python и PostgreSQL (G1, G2), отдельной инфраструктуры нет. Стоимость источников данных — в разделе 1.
- Переменные: $0 за движок. Метки MistTrack (предоплаченные пакеты, срок 1 год): $0.20 за вызов на пакете $20, $0.15 на пакете $150, $0.10 на пакете $1 000. Лимит по умолчанию — 2 вызова на расследование, до $0.40; настраивается до 4, до $0.80 (G7, G17). Arkham x402 — $0.20 за credit, метка адреса = 1 credit.
- Бесплатный план TronGrid — 100 000 запросов в сутки; лимит в секунду не опубликован, платные планы «Coming soon», Custom — по запросу. Расчёт, не измерено: граф из 1 000 адресов требует 6–10 тыс. запросов в сумме, из них к TronGrid — от примерно 3 300 (если event_index берётся из квитанции независимого узла) до 6–7 тыс. (если на каждое ребро нужен отдельный запрос событий у TronGrid). Суточной квоты тогда хватает на 14–30 таких графов; нужная средняя скорость за 5 минут — 11–24 запроса в секунду, а в пределах доли сбора данных 240 секунд (A6) — 14–29. Нужны счётчик квоты и кэш сырых ответов.
- Бесплатно только для разработки и оценки: пробный доступ Arkham (100 000 credits, 10 000 запросов меток) и TronGrid без ключа (измерено: 3 запроса в секунду, затем HTTP 429 и пауза 5 с — раздел 1).

### Ограничения и риски
- Собственное ядро — собственные ошибки: инвариант сохранения суммы из первичного исследования перепроверка опровергла — DestroyedBlackFunds уменьшает баланс без события Transfer (транзакция на 517 500 USDT). Поведение Issue и Redeem не проверено.
- Открытых меток по TRON почти нет, а критерий остановки трассировки зависит от меток: цель «≥ 95%» пока ничем не обеспечена.
- Зависимость от бесплатного тарифа TronGrid: цели «≥ 99% успешного получения данных» и «1 000 адресов за 5 минут» нельзя считать достижимыми до измерения скорости с ключом и проверки второго оператора (G5).
- FIFO требует полной истории адреса; на консолидационных кошельках и обменниках она упирается в лимит запросов. Там выдаются границы [0, min(помеченный вход, исходящий поток в окне)] с пометкой «ledger incomplete».
- Свопы USDT<->TRX и мосты выводят средства из модели одного токена; в MVP это статус «conversion, unresolved».
- Юридическая применимость FIFO и LIFO в целевых юрисдикциях не проверена; поэтому четыре методики считаются параллельно, а основную задаёт профиль юрисдикции после консультации юриста (G8).
- Ни GraphSense, ни LOCARD не публикуют метрик, где агентный слой превосходит базовый алгоритм (baseline); у платформы такого результата тоже нет (не измерено). Оценки стоимости моделей — $0.40 на типичное и $0.57 на тяжёлое расследование (раздел 5, не измерены) при лимите по умолчанию $0.40 (G17).
- Цепочка поставок: число звёзд не сигнал доверия; один из репозиториев с признаками вредоносного кода рассчитан на Windows — платформу машины разработки.
- Поиск на этапе перепроверки был ограничен: работы 2025–2026 годов по агентной трассировке и Nansen (коммерческий API меток; поддержка TRON и цены) не проверены, список альтернатив может быть неполон.

### Как проверяем качество
- Ключ ребра и фильтры — по G6. Каждое ребро, попавшее в отчёт, подтверждается квитанцией (receipt) у оператора узла, отличного от TronGrid (G5, G6); остальные рёбра сверяются выборочно. Источник event_index — /v1/transactions/{txid}/events либо порядковый номер лога в квитанции — выбирает проверка Этапа 2 (G6); от этого зависит число запросов к TronGrid.
- Тесты свойств учёта остатков (property-based): сохранение суммы с учётом DestroyedBlackFunds, Issue и Redeem; taint_fifo <= poison_upper; идемпотентность; независимость от порядка страниц API; отдельный тест на адресе с уничтоженными средствами.
- Сверка двух независимых TransferSource измеряет полноту истории адреса. Это дополнительная метрика: в критерий «≥ 99% успешного получения данных» (доля TXID тестового набора, по которым получены и проверены квитанция и события Transfer) она не входит. TronScan вторым источником не берём до письменного согласия (G5). Пересчёт части кейсов вне платформы — в Dune (таблица stablecoins_tron.transfers) или в наборе TRON в Google BigQuery (Preview) — только для оценки; их цены и свежесть не проверены.
- Сценарии: в «≥ 50 с точно известным ответом» засчитываются только синтетические сценарии на записанных ответах API и сценарии, созданные нашими собственными переводами в основной сети. Случаи с опорой на заморозки (OFAC, события blacklist Tether), публичные инциденты и тесты надёжности — отдельные классы вне этих 50. Сейчас спроектировано 25+ засчитываемых сценариев (20 синтетических и 5+ собственных); нужно ещё не менее 25.
- Тест меток — независимый набор из раздела 2 (первая версия 400–500 адресов, цель 600+) с отрицательным классом и доверительным интервалом. Собственных депозитных адресов реально получить 10–30; цель 95% с запасом они не докажут: 30 верных из 30 дают нижнюю границу Wilson 88.6%.

### Заменяемость
Высокая. Ядро работает через интерфейсы TransferSource, LabelSource и TaintPolicy: смена провайдера данных или добавление сети (Ethereum, BSC — тот же учёт по счетам; Bitcoin — вариант FIFO для UTXO) по замыслу не меняет алгоритм. Результаты всех методик хранятся, поэтому смена основной методики не требует повторного сбора данных. Коммерческие источники меток стоят за интерфейсом и отключаются без изменения ядра, но критерий остановки трассировки от меток зависит.

### Что проверить до фиксации выбора (Этап 2)
- Измерить фактическую скорость TronGrid с ключом и число запросов на стандартное расследование и на граф из 1 000 адресов. Бюджет компонента: сбор данных для графа из 1 000 адресов за 240 секунд (доля из A6) без исчерпания суточной квоты. При провале — Custom-план TronGrid или второй провайдер; изменение самой цели — только решением владельцев. Приёмка критерия времени — один сквозной замер на тестовом сервере с реальными источниками (раздел 13).
- Получить у TronGrid условия Custom-плана и письменное подтверждение допустимости SaaS-использования.
- Выбрать второй независимый TransferSource (кандидаты — в разделе 1). Критерий: полнота истории адреса против второго индекса измерена на выборке, каждое расхождение разобрано по TXID.
- Проверить event_index по G6 (не менее 1 000 TXID). Проверить по TXID, порождают ли Issue и Redeem событие Transfer и есть ли строки Approval в trc20-эндпоинте (известно только из кода crypttrace). Критерий: тест свойств на адресе с уничтоженными средствами проходит.
- Arkham: пробный доступ, письменные условия коммерческого использования и кэширования, сверка тестового набора меток. MistTrack: письменное подтверждение условий и проверка бизнес-модели (Commercial Use Review) по разделу 2.
- Полностью разобрать код crypttrace в изолированной среде до использования его кейсов. Внести в deny-list два репозитория с признаками вредоносного кода — Soniavasseur/Wallet-Risk-Scanner и harmonic101/stolen-funds-finder (код не исполнялся, вывод предварительный) — и запретить clone и pip install профильных инструментов без разбора кода.
- Консультация юриста по методике распределения смешанных средств — до выпуска черновиков обращений.
- Сравнить AI-слой с базовым алгоритмом на заранее названных подзадачах (выбор ветвей при лимите запросов, распознавание транзитных и peel-цепочек, классификация точек вывода): парное сравнение на одном наборе при одинаковом лимите бюджета, метрика — полнота найденных конечных адресов. Если выигрыша нет, результат остаётся в отчёте о метриках как невыполненный пункт критерия.
