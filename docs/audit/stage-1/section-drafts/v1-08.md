## 8. Очереди и фоновое выполнение длительных задач

**Решение.** DBOS Transact (Python) 3.2.x поверх PostgreSQL, без брокера и без платного Conductor (G2, G3). Статус: условно — до прохождения расширенного spike Этапа 2; запасной путь — Procrastinate 3.10 с собственными таблицами фронтира. Общий лимит обращений к внешним API даёт не limiter очереди DBOS, а token bucket в HTTP-шлюзе (G4): исходная рекомендация «limiter DBOS + aiolimiter» проверку кодом не выдержала. В MVP работает один процесс воркера.

### Почему выбрано
- Из проверенных вариантов без отдельного сервера только DBOS закрывает весь набор: checkpoint каждого шага в PostgreSQL и возобновление с последнего завершённого шага, cancel/resume/fork, идемпотентность по workflow ID, retries с backoff, durable timeouts, OpenTelemetry. Проверено чтением кода и документации; код не запускался.
- Результат каждого завершённого шага, включая вызов LLM, сохраняется, поэтому после сбоя он не должен исполняться и оплачиваться повторно — это работает на лимит $1 на расследование. На практике не проверено (критерий 1 spike). Для воспроизводимости нужен `DBOSPortableJSONSerializer`: по умолчанию чекпойнты пишутся в pickle.
- Лицензия MIT, релиз 3.2.0 от 2026-09-29, Python 3.10–3.14; в CI unit-тесты на SQLite и Postgres (только ubuntu) и отдельный workflow chaos-тестов.
- pydantic-ai 2.55.0 (MIT) имеет официальную durable-интеграцию с DBOS (extra `dbos>=2.10.0`) — тот же стек, что в G3.
- Брокер не нужен; `enqueue_in_transaction` ставит задачу атомарно с записью в таблицы приложения (по коду; не проверено).

### Лицензия и коммерческое использование
Библиотека DBOS Transact — MIT, коммерческий SaaS разрешён без условий. Conductor — платный SaaS; его клиент `dbos-enterprise` (PyPI 3.3.0a1 от 2026-10-01) проприетарный: DBOS Conductor Software License. В MVP он не используется. Procrastinate, aiolimiter, PyrateLimiter и throttled-py — MIT; Absurd — Apache-2.0; Valkey — BSD-3-Clause.

### Состояние проекта и расхождения «заявлено — на деле»
Проект молодой: 1 626 stars, небольшая вендорская команда, релизы почти еженедельно; мажор 3.0.0 вышел 2026-09-16 с удалением Admin Server и исправлением регрессии limiter. Расхождения найдены чтением кода:
- README утверждает, что DBOS целиком содержится в open-source библиотеке. Для исполнения это верно, но веб-консоль, алерты, управление retention и автоматический перехват работы упавшего воркера — в платном Conductor.
- Опросов два: `DEFAULT_QUEUE_POLLING_INTERVAL_SEC = 1.0` (dequeue) и `DEFAULT_POLLING_INTERVAL = 1.0` (ожидание результата дочернего workflow). Вызов, оформленный отдельным workflow в очереди, добавляет в среднем около 1 с и до 2 с в худшем случае; на 10–30 вызовах это 10–60 с при бюджете 30 с (оценка по коду, не измерено).
- Limiter — скользящее окно по числу стартов workflow, а не token bucket: на тике стартует весь остаток бюджета; выборка идёт с FOR UPDATE NOWAIT под REPEATABLE READ или SERIALIZABLE, воркеры на такой очереди сериализуются.
- Отмена: `cancel_children=False` по умолчанию, документация параметр не упоминает; отмена кооперативная (в начале следующего шага).
- Восстановление: `executor_id` по умолчанию равен `local`; процесс восстанавливает только PENDING workflow своего executor_id и своей application_version (по умолчанию — хеш исходников).
- Чекпойнты по умолчанию сериализуются через pickle + base64; все аргументы workflow попадают в системную БД вне RLS.
- Независимых отчётов о production-эксплуатации исследователь не нашёл, верификатор перепроверить не смог — не проверено; цифра «>40K workflows/steps в секунду» — вендорский бенчмарк, не измерено.

### Инфраструктура и затраты
- Процессы `api` (FastAPI, ставит задачи) и `worker` (`DBOS.launch`) в Docker на Linux.
- Расследование — родительский workflow с workflow_id, равным id расследования. Внешние вызовы на интерактивном пути — шаги внутри workflow; разрешение на вызов выдаёт шлюз G4. Limiter очереди DBOS остаётся грубым предохранителем и средством для фоновых массовых обходов.
- Token bucket: в MVP — один fetcher-процесс на провайдера с aiolimiter (при одном процессе лимит глобален по построению). При нескольких воркерах — bucket в PostgreSQL (PyrateLimiter PostgresBucket или собственная GCRA-функция с advisory lock) либо Valkey + throttled-py. Лимиты — в таблице настроек с запасом 10–20% ниже заявленных; 429 и Retry-After обрабатываются в шаге.
- Обязательная конфигурация: `DBOSPortableJSONSerializer`; `cancel_children=True`; явный `application_version`; `polling_interval_sec` 0.1–0.25 с; стабильный уникальный executor_id (`DBOS__VMID`) и restart-политика Docker; `retries_allowed=True` только для идемпотентных шагов (по умолчанию retries выключены); своя задача очистки истории.
- Выходы шагов — только идентификаторы; лимиты глубины, адресов, запросов и бюджета проверяются по таблице-счётчику перед каждым платным шагом.
- Фиксированные затраты: $0. Conductor Pro — $99/мес (1M checkpoints, далее $50 за миллион), Teams — $499/мес; не требуется (цены прочитаны 2026-10-13/14).
- Переменные затраты на стандартное расследование: $0 за саму очередь; порядка сотен шагов (оценка), 1 запись в PostgreSQL на шаг и 2 на workflow. Нагрузка на PostgreSQL при опросе 0.1–0.25 с — не измерено.
- Компонентов, бесплатных только для разработки, нет: библиотека одна и та же в разработке и в production.

### Ограничения и риски
- Цель «простая транзакция за 30 с» под угрозой при настройках по умолчанию и схеме «каждый вызов — workflow в очереди».
- При нескольких воркерах без общего bucket возможны всплески и 429; это бьёт по целям 99% получения и 1 000 адресов за 5 минут.
- Без Conductor workflow упавшего воркера ждут перезапуска именно этого воркера; при одинаковом ID `local` возможен повторный запуск чужих PENDING workflow.
- Секрет, переданный аргументом workflow, окажется в БД и бэкапах; pickle-блобы непригодны как доказательный журнал.
- Отмена без каскада оставляет платные вызовы в работе и расходует бюджет.
- Один вендор на венчурном финансировании, быстрые мажорные изменения, нет бесплатного UI, требование детерминизма тела workflow.
- pydantic-ai с DBOS: стриминг внутри workflow буферизуется, tool-функции оборачиваются в `@DBOS.step`; совместимость с DBOS 3.2.0 — не проверено. Работа DBOS на PostgreSQL 18 — не проверено (раздел 7).

### Как проверяем качество
Критерии spike; они же войдут в набор из 50+ сценариев:
1. Контейнер воркера убит посреди расследования: после перезапуска работа продолжается с последнего шага, платные вызовы не повторяются (сверка по журналу расходов).
2. Убит один из двух воркеров с уникальными executor_id: после его перезапуска нет ни дублей, ни потерянных workflow.
3. Нагрузочный тест против mock-API со счётчиком по секундным окнам при 1, 2 и 4 воркерах: максимум за любое скользящее окно не превышает лимит; 429 приводит к паузе и повтору без потери задачи.
4. Отмена расследования останавливает все дочерние задачи, resume продолжает.
5. Повторный запуск с тем же workflow ID не создаёт второго выполнения.
6. Деплой изменённого кода при незавершённых workflow с закреплённой application_version.
7. Подставной API-ключ не обнаруживается поиском по системной БД DBOS.
8. Простая транзакция укладывается в 30 с, синтетический граф на 1 000 адресов — в 5 минут при заданном лимите источника.

### Заменяемость
Средняя. Декораторы `@DBOS.workflow` и `@DBOS.step` пронизывают код оркестрации, поэтому вводим тонкий интерфейс JobRunner и держим фронтир, посещённые адреса, факты и события в таблицах приложения с идемпотентными upsert по ключу (investigation_id, address, cursor). Тогда замена на Procrastinate, Absurd или Hatchet сводится к переписыванию слоя оркестрации. Лимитер скрыт за интерфейсом «разрешение на вызов провайдера X» и заменяется легко.

### Что проверить до фиксации выбора (Этап 2)
- Spike 2–3 дня на postgres:18.6 и SQLAlchemy 2.0.54; критерий — пройдены все восемь проверок выше. При провале — Procrastinate 3.10 + собственные таблицы фронтира.
- Замер нагрузки на PostgreSQL при `polling_interval_sec` 0.1–0.25 с; критерий — цель 30 с выполняется без деградации запросов API.
- Зафиксировать место token bucket (процесс шлюза, PostgreSQL или Valkey), чтобы появление брокера не стало сюрпризом.
- Проверить pydantic-ai 2.55.0 с DBOS 3.2.0 на одном LLM-шаге (один запрос модели — один durable step).
- Проверить `enqueue_in_transaction` при схеме G2 (отдельная схема и роль DBOS) — не проверено.
- Решение владельцев: приемлема ли молодая библиотека одного вендора и нужен ли готовый веб-интерфейс мониторинга задач.
