## 4. Оркестрация AI-агентов

**Решение.** Собственный детерминированный оркестратор на DBOS Transact (сохраняемые сценарии, очереди, шаги с подтверждением человеком). Шаги модели в точках принятия решений идут через собственный интерфейс LLMClient (G13); кандидат реализации под ним — Pydantic AI, альтернатива — официальные SDK. Всё работает на том же PostgreSQL, без отдельного сервера оркестрации. Статус: условно принято (G3) — выбор фиксируется после проверочной реализации (spike) на Этапе 2, где DBOS сравнивается с вариантом без него: свои таблицы и очередь Procrastinate.

### Почему выбрано
- Требования (детерминированный поток, 100% фактов с TXID, бюджет $1, лимиты источников) описывают конвейер с сохраняемым состоянием и несколькими узкими вызовами модели, а не «автономных агентов». Паузы по бюджету, очереди с лимитами по источникам и доказательный журнал вместе не даёт ни один из рассмотренных фреймворков — их пишем сами в любом случае.
- DBOS Transact — библиотека внутри процесса приложения: чекпойнт каждого шага в PostgreSQL, восстановление с последнего завершённого шага, очереди с `limiter` и ограничением параллельности, таймеры, переживающие перезапуск, `send/recv` для подтверждения человеком и паузы по бюджету, `fork/rewind` для повторного прогона. Проверено по документации и исходному коду; код не запускался.
- Кандидат для слоя моделей — Pydantic AI: нативные провайдеры (Anthropic, OpenAI) без LiteLLM, `FallbackModel`, проверка структурированного ответа, `UsageLimits` (подтверждено чтением `usage.py`), `TestModel/FunctionModel` для тестов без сети. Учёт стоимости и журнал вызовов остаются в LLMClient.
- Перепроверка нашла дефект схемы из первичного исследования (`agent.run()` с инструментами в одном шаге): по документации DBOS из шага нельзя вызывать, запускать или ставить в очередь сценарий, поэтому вызовы инструментов обходили бы лимиты, а сбой посреди шага повторно оплачивал бы все его запросы к модели. Зафиксировано (G3, G13): решения модели по умолчанию идут без инструментов, один запрос к модели = один `@DBOS.step`; инструменты остаются только у OSINT-агента (раздел 11).
- «Роли» агентов — типизированные функции `decide(Input) -> Output`; их выход — предложение, которое принимает или отклоняет детерминированный код. Модуль проверки доказательств — не модель, а детерминированная сверка по TXID.

### Лицензия и коммерческое использование
DBOS Transact — MIT, Pydantic AI — MIT; обе подтверждены чтением файлов LICENSE. Коммерческое использование в SaaS разрешено; условие MIT — сохранять уведомление об авторских правах и текст лицензии. Зависимость Pydantic AI `httpx2` — BSD-3-Clause.

DBOS Conductor (консоль наблюдаемости, оповещения, разграничение доступа) — отдельный проприетарный продукт; библиотеке он не нужен и в MVP не используется (G3). По нашему прочтению Conductor License, на своём сервере он бесплатен только в режиме Test/Development, а production с клиентскими данными требует платного ключа. Тарифы (прочитано 2026-10-14): Pro — $99/мес, Teams — $499/мес.

### Состояние проекта и расхождения «заявлено — на деле»
**DBOS Transact:** v3.2.0 от 2026-09-29, 1 626 звёзд на GitHub, 6 открытых issues, опубликованных уведомлений о безопасности нет, в CI — модульные тесты и тесты на сбои. Расхождения:
- Восстановление работает только при совпадении версии приложения, которая по умолчанию равна хешу кода сценария: после деплоя незавершённые расследования автоматически не продолжаются.
- `limiter` ограничивает число запусков сценариев, а не HTTP-запросов; опрос очередей по умолчанию раз в 1.0 с; в 3.0.0 исправляли регрессию `limiter`.
- Мажорная версия 3.0.0 (2026-09-16) сменила схему системной БД и удалила admin server и очереди в памяти.
- Заявлена работа на Windows, но CI идёт только на Ubuntu; запуск на Windows 11 не проверен, разработка ведётся в Docker/WSL2.

**Pydantic AI:** v2.55.0 от 2026-10-09, 20 595 звёзд. Расхождения:
- Политика версий обещает минорные версии без намеренных ломающих изменений; фактический темп — 55 минорных релизов за 15.4 недели после v2.0.0 (2026-06-23), трёхмесячный порог для V3 пройден 2026-09-23.
- 16 опубликованных уведомлений о безопасности, из них 4 уровня high; два — о неполном вырезании содержимого в OTel.
- `cost_limit` срабатывает после превышения и не действует для моделей без известных цен — это лишь второй контур после собственного учёта бюджета.
- Готовая интеграция с DBOS (`DBOSDurability`) импортирует приватные модули DBOS, `DBOSAgent` помечен deprecated — её не используем (G13).

### Инфраструктура и затраты
- **Постоянные:** $0 за лицензии; новой инфраструктуры нет — системные таблицы DBOS лежат в том же PostgreSQL (отдельная схема и роль, G2), воркер работает в процессе приложения.
- **Бесплатно только для разработки:** Conductor на своём сервере. В production работаем без него: готового интерфейса нет, состояние прогонов читается через `list_workflows` / `list_workflow_steps` и собственный журнал.
- **Переменные (токены моделей).** Цены Claude API за миллион токенов, вход/выход (прочитано 2026-10-14): Haiku 5.5 — $0.10/$0.50 при запросе до 100 000 токенов, Sonnet 5.5 — $2/$10. Оценка первичного исследования, без замера: 25 решающих вызовов по ~6 000 входных и ~1 000 выходных токенов — около $0.03 на Haiku 5.5 и $0.55 на Sonnet 5.5. С циклом вызова инструментов (2–4 запроса на решение) и токенизатором новых моделей (около +30% токенов) Sonnet 5.5 на всех шагах дал бы $0.55 × 2–4 × 1.3 ≈ $1.4–2.9 — выше лимита; Haiku 5.5 — менее $0.15. Поэтому модель по умолчанию — Haiku 5.5. Узкая схема «Sonnet 5.5 только на эскалациях» оценена в $0.05–0.30 на расследование.
- **Принятая схема шире (G13):** Sonnet 5.5 — на планировании при неоднозначности и на коротких текстовых секциях отчёта. По расчёту раздела 5 она стоит $0.40 в типичном и $0.57 в тяжёлом случае (106 и 158 вызовов); это оценки, не замеры. Лимит моделей по умолчанию — $0.40 (G17): типичный случай по расчёту доходит до порога 70% ($0.28), тяжёлый в лимит не укладывается; в обоих случаях действует снижение из G17. Обе схемы замеряются на Этапе 2 (проверка 6). Платные запросы к источникам данных учтены в их разделах.
- **Трудозатраты (оценка первичного исследования, не измерены):** каркас оркестратора, учёт бюджета, журнал событий и адаптер слоя сохраняемого исполнения — 2–3 человеко-недели.

### Ограничения и риски
- **Восстановление после деплоя:** нужны явная `application_version`, `enable_patching` и процедура деплоя при незавершённых прогонах.
- **Цели по времени** (30 с, 2 мин, 1 000 адресов за 5 мин) не измерены: накладные расходы чекпойнтов и опроса очередей неизвестны. Интервал считается от старта задачи до проверенного JSON-отчёта в интерфейсе; PDF — отдельная асинхронная задача (G11).
- **Бюджет $1 (G17)** держит только собственный учёт, работающий как резервирование: перед платным вызовом в одной транзакции резервируется его максимальная стоимость (для модели — подсчитанные входные токены плюс `max_tokens` по цене выхода; для платного API — цена вызова), после ответа резерв заменяется фактом. Вызов не отправляется, если сумма фактов и резервов превысит лимит статьи или общий лимит $1.00, поэтому параллельные вызовы не могут превысить его вместе.
- **Изменчивость и цепочка поставок:** обязательны фиксация точных версий с хешами и адаптеры-изоляторы; `httpx2` (первый релиз 2026-05-11) стоит на пути всех ключей к моделям.
- **Небольшой поставщик:** по статистике GitHub у одного автора DBOS 394 коммита, у следующего — 77; облачный Conductor означал бы передачу метаданных расследований поставщику.
- **Pickle по умолчанию:** право записи в системную БД равно исполнению кода при восстановлении, изменение классов ломает чекпойнты. Решение — переносимый JSON (`DBOSPortableJSONSerializer`), в шагах только идентификаторы и примитивы.

### Как проверяем качество
- Тест на сбой: `kill -9` воркера посреди прогона; после возобновления оплаченные вызовы не повторяются.
- Повторный прогон: ответы HTTP и моделей пишутся в хранилище с адресацией по хешу содержимого; прогон только из сохранённых ответов должен давать побитово тот же граф и отчёт.
- Не менее 50 сценариев с известным правильным ответом (в счёт идут только синтетические на записанных ответах API и созданные собственными переводами в основной сети): базовый алгоритм (baseline) против AI-слоя на одних данных; шаг модели остаётся только там, где он измеримо лучше. Случаи с заморозками, публичные инциденты и тесты надёжности считаются отдельно.
- Тесты бюджета (G17): при 70% лимита моделей остаётся только Haiku 5.5, при 100% отчёт выходит без текста модели; при общем лимите прогон переходит в `PAUSED_BUDGET` с сохранением результатов и продолжается после повышения лимита. Резервирование: 20 параллельных вызовов при остатке на 5 — отправлено не больше 5, итог не выше лимита.
- Тесты на внедрение инструкций (prompt injection) через имена токенов, memo, теги адресов и OSINT-страницы: план и метки не меняются.
- Тест утечек ключей и сверка полноты журнала вызовов со шлюзом — раздел 11.

### Заменяемость
Для слоя моделей — высокая; для слоя сохраняемого исполнения — средняя, как в разделе 8: декораторы DBOS пронизывают код оркестрации, поэтому вводится тонкий интерфейс JobRunner (сценарии, шаги, очереди, `send/recv`). Шаги — обычные Python-функции; схема «сценарий — шаг» переносится на Temporal (workflow/activity). Трудоёмкость перехода на вариант без DBOS не измерена, оценивается в проверочной реализации. Слой моделей изолирован интерфейсом LLMClient и функциями `decide(Input) -> Output`: замена Pydantic AI на официальные SDK провайдеров, OpenAI Agents SDK или тонкие библиотеки типизированных вызовов (BAML, Instructor, Mirascope; встроенных `UsageLimits` и `TestModel` у них нет) затрагивает один модуль. Базовый алгоритм трассировки не зависит ни от одной из библиотек.

### Что проверить до фиксации выбора (Этап 2)
Проверочная реализация на 2–3 дня в Docker/WSL2 с реальным ключом TronGrid. Её проверки — бюджеты компонента, а не приёмка: приёмка целей по времени — один сквозной замер на тестовом сервере с реальными источниками (часть A, A8).
1. `kill -9` посреди прогона — критерий: 0 повторных платных вызовов после возобновления.
2. Деплой новой версии посреди прогона (явная `application_version`, `enable_patching`, чекпойнты в переносимом JSON) — критерий: расследование продолжается без ручного вмешательства.
3. Граф на 1 000 адресов: накладные расходы чекпойнтов и влияние `polling_interval_sec` — критерий: слой очередей и чекпойнтов укладывается в свою долю бюджета времени, заданную до замера.
4. Лимиты провайдеров — критерий: 0 ответов 429 при заданном лимите (общий ограничитель в шлюзе, раздел 11).
5. Тот же сценарий на варианте без DBOS. Правило решения (G3): если оба варианта проходят проверки этого раздела и раздела 8, берётся более простой — по оценке перепроверки, вариант без DBOS; если проходит один — он.
6. Замер числа запросов к модели и токенов на стандартное расследование для обеих схем — ориентиры: «Sonnet 5.5 только на эскалациях» — не выше $0.30; схема G13 — не выше лимита моделей $0.40 (G17). Разница в числе вызовов (25 против 106) закрывается замером. Здесь же выбирается реализация под LLMClient: Pydantic AI или официальные SDK.
7. Решения владельцев: кто вправе повышать лимит после паузы — пользователь или оператор; перечень действий, требующих подтверждения человеком (по умолчанию — любая отправка обращений: платформа готовит только черновики).
