## 8. Очереди и фоновое выполнение длительных задач

**Решение.** DBOS Transact (Python) 3.2.x поверх PostgreSQL, без брокера и без платной консоли Conductor (G2, G3). DBOS — библиотека, которая записывает результат каждого шага расследования в PostgreSQL и после сбоя продолжает с последнего завершённого шага. Статус: условно — на Этапе 2 DBOS сравнивается с вариантом без него (свои таблицы и очередь задач Procrastinate 3.10); если проверки проходят оба, берётся более простой (G3). Общий лимит обращений к внешним API держит не лимит очереди DBOS, а ограничитель запросов в HTTP-шлюзе (G4): связку «лимит очереди DBOS и aiolimiter» из первичного исследования перепроверка отклонила после чтения кода. В MVP работает один процесс воркера.

### Почему выбрано
- Из проверенных вариантов без отдельного сервера только DBOS закрывает весь набор: чекпойнт каждого шага в PostgreSQL и возобновление с последнего завершённого шага, отмена, возобновление и ветвление (cancel/resume/fork), идемпотентность по workflow ID, повторы с нарастающей паузой, сохраняемые тайм-ауты, OpenTelemetry. Workflow здесь и далее — термин DBOS: сохраняемая последовательность шагов. Проверено чтением кода и документации; код не запускался.
- Результат каждого завершённого шага, включая вызов модели, сохраняется, поэтому после сбоя он не должен исполняться и оплачиваться повторно — это работает на лимит $1 на расследование (G17). На практике не проверено (проверка 1). Для воспроизводимости нужен `DBOSPortableJSONSerializer`: по умолчанию чекпойнты пишутся в pickle.
- Лицензия MIT, релиз 3.2.0 от 2026-09-29, Python 3.10–3.14; в CI модульные тесты на SQLite и PostgreSQL (только ubuntu) и отдельный набор тестов со сбоями (chaos).
- Специальная интеграция с библиотекой агентов не нужна: один запрос к модели — обычный сохраняемый шаг `@DBOS.step` (G13). Готовая интеграция pydantic-ai 2.55.0 с DBOS (extra `dbos>=2.10.0`) не используется; причины — в разделе 4.
- Брокер не нужен; `enqueue_in_transaction` ставит задачу атомарно с записью в таблицы приложения (по коду; на практике не проверено).

### Состояние проекта и расхождения «заявлено — на деле»
Проект молодой: 1 626 звёзд на GitHub, небольшая команда вендора (по статистике коммитов), релизы почти еженедельно; мажор 3.0.0 вышел 2026-09-16 с удалением Admin Server и исправлением регрессии лимита очереди. Расхождения найдены чтением кода:
- README утверждает, что DBOS целиком содержится в открытой библиотеке. Для исполнения это верно, но веб-консоль, оповещения, управление сроком хранения истории и автоматический перехват работы упавшего воркера — в платном Conductor.
- Опросов два: `DEFAULT_QUEUE_POLLING_INTERVAL_SEC = 1.0` (выборка из очереди) и `DEFAULT_POLLING_INTERVAL = 1.0` (ожидание результата дочернего workflow). Вызов, оформленный отдельным workflow в очереди, добавляет в среднем около 1 с и до 2 с в худшем случае; на 10–30 вызовах это 10–60 с при цели 30 с (оценка по коду, замера нет).
- Лимит очереди (limiter) — скользящее окно по числу стартов workflow, а не равномерный ограничитель (token bucket): на тике стартует весь остаток бюджета; выборка идёт с FOR UPDATE NOWAIT под REPEATABLE READ или SERIALIZABLE, и воркеры на такой очереди работают по очереди, а не параллельно.
- Отмена: `cancel_children=False` по умолчанию, документация параметр не упоминает; отмена срабатывает только в начале следующего шага.
- Восстановление: `executor_id` по умолчанию равен `local`; процесс восстанавливает только незавершённые (PENDING) workflow своего executor_id и своей application_version (по умолчанию — хеш исходников).
- Чекпойнты по умолчанию сериализуются через pickle и base64; все аргументы workflow попадают в системную БД вне RLS.
- Независимых отчётов о production-эксплуатации не найдено (поиск неполон); цифра «более 40 000 workflows и шагов в секунду» — бенчмарк вендора, нами не измерена.

### Инфраструктура и затраты
- Процессы `api` (FastAPI, ставит задачи) и `worker` (`DBOS.launch`) в Docker на Linux.
- Расследование — родительский workflow с workflow_id, равным id расследования. Внешние вызовы на интерактивном пути — шаги внутри workflow, а не отдельные задачи очереди; разрешение на вызов выдаёт шлюз (G4). Лимит очереди DBOS остаётся грубым предохранителем и средством для фоновых массовых обходов.
- Ограничитель запросов: в MVP — aiolimiter внутри HTTP-шлюза в единственном процессе воркера (G4); при одном процессе лимит общий по построению. При нескольких воркерах — общий ограничитель в PostgreSQL (PyrateLimiter PostgresBucket или собственная SQL-функция с advisory lock) либо Valkey и throttled-py. Лимиты — в таблице настроек с запасом 10–20% ниже заявленных провайдером; ответы 429 и Retry-After обрабатываются в шаге.
- Обязательная конфигурация: `DBOSPortableJSONSerializer`; `cancel_children=True`; явный `application_version`; `polling_interval_sec` 0.1–0.25 с; стабильный уникальный executor_id (`DBOS__VMID`) и политика перезапуска Docker; `retries_allowed=True` только для идемпотентных шагов (по умолчанию повторы выключены); своя задача очистки истории.
- Выходы шагов — только идентификаторы. Лимиты глубины, адресов и запросов проверяются по таблице-счётчику перед каждым шагом; бюджет — резервированием максимальной стоимости до отправки платного вызова (G17).
- Фиксированные затраты: $0. Conductor Pro — $99/мес (1 млн чекпойнтов, далее $50 за миллион), Teams — $499/мес; не требуется (цены прочитаны 2026-10-13/14).
- Переменные затраты на стандартное расследование: $0 за саму очередь; порядка сотен шагов (оценка), 1 запись в PostgreSQL на шаг и 2 на workflow. Нагрузка на PostgreSQL при опросе 0.1–0.25 с не измерена.
- Компонентов, бесплатных только для разработки, нет: библиотека одна и та же в разработке и в production.

### Ограничения и риски
- Цель «простая транзакция за 30 с» под угрозой при настройках по умолчанию и схеме «каждый вызов — workflow в очереди».
- При нескольких воркерах без общего ограничителя возможны всплески и ответы 429; это бьёт по целям «99% успешного получения данных» и «1 000 адресов за 5 минут».
- Без Conductor workflow упавшего воркера ждут перезапуска именно этого воркера; при одинаковом ID `local` возможен повторный запуск чужих незавершённых workflow. В MVP с одним воркером это закрывается его перезапуском (на практике не проверено).
- Без обязательной конфигурации секрет из аргументов workflow попадает в БД и резервные копии, данные в pickle непригодны как доказательный журнал, а отмена не останавливает уже поставленные платные вызовы.
- Один вендор с небольшой командой, быстрые мажорные изменения, нет бесплатного веб-интерфейса, требование детерминизма тела workflow.
- Схема «один запрос к модели — один сохраняемый шаг» на DBOS 3.2.0 и работа DBOS на PostgreSQL 18 не проверены (раздел 7).

### Как проверяем качество
Проверки проверочной реализации (spike); их проходят оба варианта — с DBOS и без него. Они же войдут в регрессионные тесты надёжности — отдельный класс, вне 50 сценариев трассировки с известным правильным ответом:
1. Контейнер воркера убит посреди расследования: после перезапуска работа продолжается с последнего шага, платные вызовы не повторяются (сверка по журналу расходов).
2. Убит один из двух воркеров (для DBOS — с уникальными executor_id): после его перезапуска нет ни дублей, ни потерянных задач.
3. Нагрузочный тест против имитации API (mock) со счётчиком по секундным окнам при 1, 2 и 4 воркерах: максимум за любое скользящее окно не превышает лимит; ответ 429 приводит к паузе и повтору без потери задачи.
4. Отмена расследования останавливает все дочерние задачи, возобновление продолжает работу.
5. Повторный запуск с тем же идентификатором расследования не создаёт второго выполнения.
6. Выкладка изменённого кода при незавершённых расследованиях (для DBOS — с закреплённой application_version).
7. Подставной API-ключ не обнаруживается поиском по системным таблицам очереди.
8. Бюджет компонента: накладные расходы очереди и чекпойнтов на простой транзакции и на синтетическом графе из 1 000 адресов (имитация API при заданном лимите источника) укладываются в долю времени, заданную до замера.

Проверка 8 — не приёмка целей «30 с» и «5 минут»: приёмка — один сквозной замер на тестовом сервере с реальными источниками (протокол — раздел 13).

### Заменяемость
Средняя. Декораторы `@DBOS.workflow` и `@DBOS.step` пронизывают код оркестрации, поэтому вводим тонкий интерфейс JobRunner и держим очередь адресов на обход, посещённые адреса, факты и события в таблицах приложения с идемпотентной записью по ключу (investigation_id, address, cursor). Тогда замена на Procrastinate, Absurd или Hatchet сводится к переписыванию слоя оркестрации. Ограничитель скрыт за интерфейсом «разрешение на вызов провайдера X» и заменяется легко.

### Что проверить до фиксации выбора (Этап 2)
- Проверочная реализация на postgres:18.6 и SQLAlchemy 2.0.54 в двух вариантах: DBOS (2–3 дня, оценка) и свои таблицы с очередью Procrastinate 3.10. Критерий — пройдены все восемь проверок выше; если их проходят оба варианта, берётся более простой (G3), если один — он.
- Замер нагрузки на PostgreSQL при `polling_interval_sec` 0.1–0.25 с; критерий — запросы API не замедляются, а накладные расходы очереди укладываются в свою долю цели 30 с.
- Зафиксировать место общего ограничителя при нескольких воркерах (PostgreSQL или Valkey), чтобы появление брокера не стало сюрпризом.
- Проверить один запрос к модели через LLMClient внутри `@DBOS.step` (один запрос модели — один сохраняемый шаг).
- Проверить `enqueue_in_transaction` при схеме G2 (отдельная схема и роль DBOS): постановка задачи атомарна с записью в таблицы приложения.
- Решение владельцев: приемлема ли молодая библиотека одного вендора и нужен ли готовый веб-интерфейс мониторинга задач (вариант по умолчанию — без него: SQL по системным таблицам и OpenTelemetry).
