## 11. Механизм подключения внешних инструментов к агентам

**Решение.** Внешние источники подключаются как in-process типизированные function tools через собственный реестр инструментов и единый HTTP-шлюз (общий token bucket на провайдера, хранилище сырых ответов, редакция ключей). MCP — только опциональный адаптер на границе, выключенный по умолчанию, и возможный будущий внешний интерфейс платформы. Статус: принято; перепроверка аудита оставила рекомендацию в силе без существенных оговорок.

### Почему выбрано
- Доказательная платформа должна владеть HTTP-слоем: хранить сырой ответ первичного источника для каждого факта, управлять ключами, лимитами и повторами, воспроизводить прогон из fixtures. MCP-сервер между кодом и API отнимает этот контроль и не добавляет данных: по документации официальные TRON-серверы — обёртки над теми же REST API.
- TronGrid MCP проверен по официальной документации: 149 инструментов, включая `broadcastTransaction`, `deployContract` и `freezeBalanceV2`; код закрыт, лимиты и условия использования не опубликованы.
- Сторонние серверы проверены чтением репозиториев и текстов лицензий: у MistTrackMCP нет файла лицензии, тестов и CI, а ключ уходит в URL; лицензия Blockscout MCP запрещает коммерческое и SaaS-использование; Bitquery MCP закрыт и требует интерактивного OAuth.
- Протокол нестабилен: ревизия 2026-07-28 ломающая (убраны сессии и handshake `initialize`); у MCP python-sdk 12 advisories, из них 9 high; спецификация сама признаёт, что не может обеспечить безопасность на уровне протокола.
- Live-пробы 2026-10-13/14: keyless GET к TronGrid — HTTP 200 за 0.49–0.51 с; keyless GET к TronScan — HTTP 429 с блокировкой на 50 с на единственный запрос (IP был общим с параллельными проверками). Прямой REST прост и быстр, а лимиты и ключи надо держать самим с первого дня.
- Поправка перепроверки: довод о несовместимости 149 описаний инструментов с бюджетом $1 преувеличен — список можно фильтровать. Решающие причины — контроль сырого ответа, write-поверхность, закрытый код и отсутствие условий использования.

### Лицензия и коммерческое использование
Реестр инструментов и HTTP-шлюз — собственный код, лицензионных ограничений нет. Используемые библиотеки: Pydantic AI — MIT (регистрация function tools, схемы, toolsets), vcrpy — MIT (тестовый record/replay). Если MCP-граница когда-либо включается: MCP python-sdk — MIT, FastMCP — Apache-2.0, snyk/agent-scan и agentgateway — Apache-2.0, docker/mcp-gateway — MIT (у трёх последних проверены только metadata). Коммерческие ограничения задают только условия самих API-провайдеров; они разобраны в разделах 1 и 2.

### Состояние проекта и расхождения «заявлено — на деле»
Решение — паттерн, а не продукт; его поддержка в Pydantic AI подтверждена листингом каталога `toolsets/` (function, filtered, approval_required, prefixed). Расхождения найдены у отклонённых вариантов:
- TronGrid MCP не read-only и работает на ревизии протокола 2025-11-25 с handshake, то есть на устаревшей модели; для Claude Desktop его docs советуют `mcp-remote` — пакет, у которого была CVE-2025-6514 (CVSS 9.6).
- Blockscout MCP в каталогах описан как open-source; с 2026-05-15 действует ограничительная лицензия.
- MCP python-sdk: v2.3.0 от 2026-10-02; 9 из 12 advisories опубликованы в 2026 году, 5 — за 2026-09-28..2026-10-05.
- Официальных MCP-серверов Arkham, Chainalysis, TRM и Elliptic поиском не найдено (отсутствие не доказано); найденные обёртки — любительские, с 0–1 звездой.
- Не проверено: `tools/list` официальных TRON MCP-серверов не вызывался, описания инструментов на tool poisoning не проверялись; число инструментов TronScan MCP (119) и версия его протокола известны только из поискового сниппета.

### Инфраструктура и затраты
- **Постоянные:** $0 за лицензии; новой инфраструктуры нет — реестр и шлюз работают в процессе приложения, сырые ответы пишутся в хранилище доказательств.
- **Переменные:** сам механизм не добавляет стоимости на расследование; платные запросы тарифицируют провайдеры (см. разделы 1 и 2). Экономия от узкого набора инструментов (3–8 вместо 100–149 описаний) оценена в 10–30 тыс. входных токенов на вызов модели — не измерено; оценка относится к нефильтрованному списку MCP-сервера.
- **Состав собственного кода:** реестр (pydantic-модели входа и выхода и политика каждого инструмента: side effect, класс стоимости, провайдер, `requires_approval`, роли); шлюз (ключи в заголовки в последний момент, retry/backoff, token bucket, запись сырого ответа, режимы live / record / replay); для LLM — компактные сводки со ссылками `raw_ref`, `source`, `fetched_at`.
- **Трудозатраты (оценка аудита, не измерено):** 10–15 типизированных клиентов эндпоинтов, шлюз и реестр — 1.5–2.5 человеко-недели.
- **Бесплатно только для разработки:** в самом механизме платных компонентов нет. Keyless-доступ к API не годится и для разработки: TronGrid ответил на единичную пробу, TronScan на единственный запрос вернул 429; ключи провайдеров нужны с первого дня.

### Ограничения и риски
- Клиенты под каждый API пишет и поддерживает команда; изменения API ловятся контрактными тестами.
- Поля из блокчейна и эксплореров (имена токенов, memo, публичные теги) и OSINT-страницы остаются каналом prompt injection и при прямых вызовах: нужны типизация, ограничение длины, пометка недоверенных полей и запрет менять план по содержимому результатов.
- Limiter очередей DBOS считает старты workflow, а не HTTP-запросы, поэтому лимит держит один token bucket в шлюзе, которым пользуются и очереди, и инструменты.
- Два HTTP-стека в одном процессе: аудит предлагал `httpx`, а Pydantic AI перешёл на `httpx2` (пакету 5 месяцев). Нужен один HTTP-клиент для собственного кода и lock-файл с хэшами.
- MistTrack OpenAPI принимает ключ в URL — нужна отдельная редакция query string в шлюзе.
- Все инструменты read-only, действий с подписью и трансляцией транзакций в системе нет; LLM получает инструменты только в OSINT-агенте, остальные вызовы делает детерминированный код через тот же шлюз (раздел 4).

### Как проверяем качество
- Контрактные тесты каждого клиента на записанных fixtures (vcrpy или pytest-recording) и периодический live-smoke с проверкой схемы ответа.
- Перекрёстная сверка по выборке TXID (сумма, отправитель, получатель, блок, время) между TronGrid и независимым оператором узла из раздела 1. Аудит этой области предлагал сверку с TronScan; по общему решению TronScan исключён из критического пути, поэтому пара источников заменена.
- Каждая запись сырого ответа содержит sha256, URL без секретов, статус, `fetched_at` и источник; верификатор отклоняет любой факт отчёта без ссылки на такую запись.
- Полнота аудита: число записей вызовов инструментов в журнале равно числу запросов, зафиксированных шлюзом.
- Тесты на prompt injection и тест утечек (шаблоны ключей в логах, трассах, отчётах и сохранённых URL).
- Если MCP-сервер всё же разрешается: фиксируются список инструментов и sha256 их описаний и схем, при расхождении сервер отключается; только read-only; результаты проходят тот же санитайзер; периодическое сканирование (snyk/agent-scan).

### Заменяемость
Высокая. Реестр инструментов не зависит от транспорта: любой инструмент можно выставить наружу через MCP (официальный mcp SDK v2 или FastMCP) либо заменить провайдера за адаптером без изменений в агентах и оркестраторе. MCP-адаптер можно включить или убрать, не затрагивая ядро. Будущий собственный MCP-сервер платформы аудит описывает как read-only, с OAuth 2.1 и проверкой audience, на ревизии 2026-07-28.

### Что проверить до фиксации выбора (Этап 2)
1. Прототип шлюза с единым token bucket под нагрузкой с реальными ключами провайдеров — критерий: 0 ответов 429 при заданном лимите.
2. Record/replay — критерий: прогон cache-only даёт побитово тот же граф и отчёт.
3. Тест редакции — критерий: 0 совпадений с шаблонами ключей в логах, трассах, отчётах и сохранённых URL, включая ключ MistTrack в query string.
4. Выбор одного HTTP-клиента; совместимость vcrpy или pytest-recording с ним — не проверено, критерий: записанные fixtures воспроизводятся без сети. Lock-файл с хэшами для `httpx2`, `anthropic`, `openai`.
5. Решения владельцев: нужен ли будущий MCP-сервер платформы для клиентов; допустим ли ручной доступ аналитиков через сторонние MCP-серверы в dev-среде.
6. Если MCP включается: письменные условия использования сервера, allowlist, pinning описаний, прокси (agentgateway или docker/mcp-gateway), запрет `mcp-remote`.
