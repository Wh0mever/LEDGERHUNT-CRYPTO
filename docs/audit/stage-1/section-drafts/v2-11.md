## 11. Механизм подключения внешних инструментов к агентам

**Решение.** Внешние источники подключаются как типизированные функции в процессе приложения через собственный реестр инструментов и единый HTTP-шлюз: общий ограничитель запросов на провайдера, хранилище сырых ответов как доказательств, вырезание ключей (G4). MCP (Model Context Protocol — открытый протокол подключения инструментов к моделям) — только необязательный адаптер на границе, выключенный по умолчанию, и возможный будущий внешний интерфейс платформы. Статус: принято; перепроверка оставила решение в силе без существенных оговорок.

### Почему выбрано
- Доказательная платформа должна владеть HTTP-слоем: хранить сырой ответ первичного источника для каждого факта, управлять ключами, лимитами и повторами, воспроизводить прогон из записанных ответов. MCP-сервер между кодом и API отнимает этот контроль и не добавляет данных: по документации официальные MCP-серверы TRON — обёртки над теми же REST API.
- TronGrid MCP проверен по официальной документации: 149 инструментов, включая `broadcastTransaction`, `deployContract` и `freezeBalanceV2`; код закрыт, лимиты и условия использования не опубликованы.
- Сторонние серверы проверены чтением репозиториев и текстов лицензий: у MistTrackMCP нет файла лицензии, тестов и CI, а ключ передаётся в URL; лицензия Blockscout MCP, по нашему прочтению, запрещает коммерческое и SaaS-использование; у Bitquery MCP кода сервера в репозитории нет, вход — только интерактивный OAuth.
- Протокол нестабилен: ревизия 2026-07-28 ломающая (убраны сессии и handshake `initialize`); у MCP python-sdk опубликовано 12 уведомлений о безопасности (advisories), из них 9 уровня high; спецификация сама признаёт, что не может обеспечить безопасность на уровне протокола.
- Живые пробы 2026-10-13/14 без ключа: GET к TronGrid — HTTP 200 за 0.49–0.51 с; GET к TronScan — HTTP 429 с блокировкой на 50 с на единственный запрос (IP был общим с параллельными проверками). Прямой REST прост и быстр, а лимиты и ключи надо держать самим с первого дня.
- Число описаний инструментов (149) — не решающий довод: список можно фильтровать. Решающие причины — контроль сырого ответа, инструменты отправки транзакций, закрытый код и отсутствие условий использования.

### Лицензия и коммерческое использование
Реестр инструментов и HTTP-шлюз — собственный код, лицензионных ограничений нет. Кандидат для регистрации инструментов и их схем — Pydantic AI, MIT (выбор реализации — G13); для тестовой записи и повторного прогона — vcrpy, MIT. Условие MIT — сохранять уведомление об авторских правах и текст лицензии. Если MCP-граница когда-либо включается: MCP python-sdk — MIT, FastMCP — Apache-2.0, сканер описаний snyk/agent-scan и прокси agentgateway — Apache-2.0, прокси docker/mcp-gateway — MIT (у трёх последних проверены только метаданные). Ограничения на коммерческое использование задают условия самих API-провайдеров; они разобраны в разделах 1 и 2.

### Состояние проекта и расхождения «заявлено — на деле»
Решение — приём проектирования, а не продукт; его поддержка в Pydantic AI подтверждена списком файлов каталога `toolsets/` (function, filtered, approval_required, prefixed). Расхождения найдены у отклонённых вариантов:
- TronGrid MCP не ограничен чтением и работает на ревизии протокола 2025-11-25 с handshake, то есть на прежней модели; для Claude Desktop его документация советует `mcp-remote` — пакет, у которого была CVE-2025-6514 (CVSS 9.6).
- Blockscout MCP в каталогах описан как open-source; с 2026-05-15 действует ограничительная лицензия.
- MCP python-sdk: v2.3.0 от 2026-10-02; 9 из 12 уведомлений о безопасности опубликованы в 2026 году, 5 — за 2026-09-28..2026-10-05.
- Официальных MCP-серверов Arkham, Chainalysis, TRM и Elliptic поиском не найдено (отсутствие не доказано); найденные репозитории с названиями этих компаний — сторонние обёртки с 0–1 звездой, их код не читался.
- Не проверено: `tools/list` официальных TRON MCP-серверов не вызывался, описания инструментов на скрытые инструкции (tool poisoning) не проверялись; число инструментов TronScan MCP (119) и версия его протокола известны только из поисковой выдачи.

### Инфраструктура и затраты
- **Постоянные:** $0 за лицензии; новой инфраструктуры нет — реестр и шлюз работают в процессе приложения, сырые ответы пишутся в хранилище доказательств.
- **Переменные:** сам механизм не добавляет стоимости на расследование; платные запросы тарифицируют провайдеры (разделы 1 и 2). Экономия от узкого набора инструментов (3–8 вместо 100–149 описаний) оценена в 10–30 тыс. входных токенов на вызов модели и не измерена; оценка относится к нефильтрованному списку MCP-сервера.
- **Состав собственного кода:** реестр (pydantic-модели входа и выхода и политика каждого инструмента: побочный эффект, класс стоимости, провайдер, `requires_approval`, роли); шлюз (ключи подставляются в заголовки в последний момент, повторы с нарастающей паузой, общий ограничитель запросов, запись сырого ответа, режимы live / record / replay); для модели — компактные сводки со ссылками `raw_ref`, `source`, `fetched_at`. Платный вызов шлюз отправляет только после резервирования его стоимости в учёте бюджета (G17, раздел 4).
- **Трудозатраты (оценка первичного исследования, не измерены):** 10–15 типизированных клиентов эндпоинтов, шлюз и реестр — 1.5–2.5 человеко-недели.
- **Бесплатно только для разработки:** в самом механизме платных компонентов нет. Доступ без ключа не годится и для разработки: TronGrid без ключа держит 3 запроса в секунду, затем HTTP 429 и пауза 5 с (замер раздела 1), TronScan вернул 429 на единственный запрос. Ключи провайдеров нужны с первого дня.

### Ограничения и риски
- Клиенты под каждый API пишет и поддерживает команда; изменения API ловятся контрактными тестами.
- Поля из блокчейна и обозревателей блоков (имена токенов, memo, публичные теги) и OSINT-страницы остаются каналом внедрения инструкций и при прямых вызовах: нужны типизация, ограничение длины, пометка недоверенных полей и запрет менять план по содержимому результатов.
- `limiter` очередей DBOS считает запуски сценариев, а не HTTP-запросы, поэтому лимит держит один ограничитель в шлюзе, которым пользуются и очереди, и инструменты. В MVP он работает в единственном процессе воркера (G4); при втором процессе его придётся вынести в общее хранилище (раздел 8).
- Два HTTP-стека в одном процессе: для собственного кода планировался `httpx`, а Pydantic AI перешёл на `httpx2` (пакету 5 месяцев). Нужен один HTTP-клиент для собственного кода и файл фиксации версий с хешами.
- MistTrack OpenAPI принимает ключ в URL — нужно отдельное вырезание ключа из строки запроса в шлюзе.
- Все инструменты только читают данные, подписи и отправки транзакций в системе нет (G16); модель получает инструменты только в OSINT-агенте, остальные вызовы делает детерминированный код через тот же шлюз (раздел 4).

### Как проверяем качество
- Контрактные тесты каждого клиента на записанных ответах (vcrpy или pytest-recording) и периодическая живая проверка схемы ответа.
- Каждое ребро, попавшее в отчёт, подтверждается квитанцией у оператора узла, отличного от TronGrid (сумма, отправитель, получатель, блок, время); остальные рёбра графа сверяются выборочно (G6).
- Каждая запись сырого ответа содержит sha256, URL без секретов, статус, `fetched_at` и источник; модуль проверки доказательств отклоняет любой факт отчёта без ссылки на такую запись.
- Полнота журнала: число записей вызовов инструментов в журнале равно числу запросов, зафиксированных шлюзом.
- Тест разрешений: вызов инструмента с побочным эффектом без записи об одобрении отклоняется и попадает в журнал (в MVP таких инструментов нет).
- Тест отказа источника: при принудительном отказе каждого провайдера отчёт называет ограничение — источник и затронутые адреса.
- Тесты на внедрение инструкций и тест утечек: шаблоны ключей и подставная seed-фраза не находятся в логах, журналах вызовов, отчётах и сохранённых URL (G16).
- Если MCP-сервер всё же разрешается: фиксируются список инструментов и sha256 их описаний и схем, при расхождении сервер отключается; только чтение; результаты проходят тот же фильтр; периодическое сканирование (snyk/agent-scan).

### Заменяемость
Высокая. Реестр инструментов не зависит от транспорта: любой инструмент можно выставить наружу через MCP (официальный mcp SDK v2 или FastMCP) либо заменить провайдера за адаптером без изменений в агентах и оркестраторе. MCP-адаптер можно включить или убрать, не затрагивая ядро. Собственный MCP-сервер платформы, если владельцы решат его делать, — только чтение, OAuth 2.1 с проверкой audience, ревизия протокола 2026-07-28.

### Что проверить до фиксации выбора (Этап 2)
1. Прототип шлюза с общим ограничителем под нагрузкой с реальными ключами провайдеров — критерий: 0 ответов 429 при заданном лимите. Это бюджет компонента; приёмка целей по времени — один сквозной замер (часть A, A8). Отдельно — смешанная нагрузка (простая задача во время обхода графа на 1 000 адресов): если простая задача не укладывается в свою цель, в ограничитель вводится приоритет интерактивных запросов.
2. Запись и повторный прогон — критерий: прогон только из сохранённых ответов даёт побитово тот же граф и отчёт.
3. Тест вырезания ключей — критерий: 0 совпадений с шаблонами ключей в логах, журналах вызовов, отчётах и сохранённых URL, включая ключ MistTrack в строке запроса.
4. Выбор одного HTTP-клиента; совместимость vcrpy или pytest-recording с ним не проверена — критерий: записанные ответы воспроизводятся без сети. Файл фиксации версий с хешами для `httpx2`, `anthropic`, `openai`.
5. Решения владельцев: нужен ли MCP-сервер платформы для клиентов (по умолчанию — нет); допустим ли ручной доступ аналитиков через сторонние MCP-серверы в среде разработки (по умолчанию — нет).
6. Если MCP включается: письменные условия использования сервера, список разрешённых серверов, фиксация описаний, прокси (agentgateway или docker/mcp-gateway), запрет `mcp-remote`.
