## 7. Реляционное хранилище

**Решение.** PostgreSQL 18 (минор 18.6), self-hosted в Docker на том же сервере, — единственная СУБД MVP (G2): данные приложения, графовые таблицы, журнал событий и системные таблицы durable-очереди. Слой доступа — SQLAlchemy 2.0.54 + Alembic 1.20 с ручными SQL-миграциями, драйвер по умолчанию — psycopg 3; изоляция расследований — RLS с FORCE; журнал — только на добавление, с цепочкой хешей. Статус: принято; переход на SQLAlchemy 2.1 и добавление asyncpg — только после проверок Этапа 2.

### Почему выбрано
- Один движок закрывает потребности MVP без брокера: RLS, JSONB для сырых ответов провайдеров, LISTEN/NOTIFY, FOR UPDATE SKIP LOCKED, встроенный sha256() и триггеры. Основание — документация PostgreSQL 18.6 (прочитаны страницы о версиях, RLS и NOTIFY); на живой БД ничего не запускалось.
- Версия 18.6 (минор от 2026-08-13), мажор 18 поддерживается до 2030-11-14. PostgreSQL 19 на 2026-10-14 — только Beta 4 от 2026-09-24, поэтому не берём.
- RLS — второй рубеж защиты: при включённой RLS без политик действует default-deny, забытый контекст даёт пустой результат, а не утечку. Ошибочный запрос, в том числе сформированный инструментом LLM-агента, не вернёт чужие строки.
- SQLAlchemy и Alembic — MIT; явные транзакции позволяют ставить контекст RLS через `set_config(..., true)` в начале каждой транзакции. DBOS (раздел 8) сам зависит от `sqlalchemy[asyncio]>=2.0.43`, то есть ORM в проекте один.
- Версия 2.0.54 (2026-09-15), а не 2.1.x: `pdm.lock` DBOS фиксирует 2.0.50, а серия 2.1 вышла 2026-09-24 и за три недели получила четыре патча. Совместимость DBOS 3.2.0 с 2.1 — не проверено.
- Журнал строится штатными средствами (REVOKE, триггеры, sha256) без новых сервисов; та же таблица событий с монотонным id питает SSE (раздел 10).

### Состояние проекта и расхождения «заявлено — на деле»
У самого PostgreSQL расхождений не найдено. Зрелость: мажор 18 вышел 2025-09-25; SQLAlchemy 2.0.54 — от 2026-09-15, Alembic 1.20.0 — от 2026-09-11, у обоих по 5 CI workflows. Важны условия эксплуатации:
- Ловушки RLS из документации: superuser и роли BYPASSRLS всегда обходят RLS; владелец таблицы обходит её без FORCE ROW LEVEL SECURITY; проверки FK и unique обходят RLS (covert channel); политики с подзапросами подвержены гонкам на READ COMMITTED.
- В официальном образе postgres:18 изменён путь данных: VOLUME /var/lib/postgresql, PGDATA=/var/lib/postgresql/18/docker (раньше /var/lib/postgresql/data). Compose со старым путём не сохранит данные при пересоздании контейнера.
- Тезис «переезд на managed Postgres — смена строки подключения» верен только для прямого соединения: production checklist DBOS запрещает transaction-mode pooler, а pooled-эндпоинты Neon и Supabase именно такие.
- CI DBOS использует образ sibedge/postgres-plv8 без явной версии: работа DBOS на PostgreSQL 18 — не проверено (у Procrastinate PostgreSQL 18 в матрице CI есть).
- Alembic autogenerate не видит политики RLS, триггеры, функции и GRANT — их пишем вручную через op.execute.
- Цепочка хешей без внешней привязки доказывает только внутреннюю согласованность: владелец БД может пересчитать её целиком (tamper-evident, не tamper-proof).
- Ничего не разворачивалось: накладные расходы RLS и скорость запросов — не измерено.

### Инфраструктура и затраты
- Один контейнер postgres:18.6, том на /var/lib/postgresql. Одна база: схема приложения под RLS и отдельная схема с отдельной ролью для системных таблиц DBOS (G2).
- Роли: owner (миграции), app (API и воркеры; не владелец таблиц, без BYPASSRLS), maintenance (BYPASSRLS, только служебные задачи), dbos (без доступа к схеме приложения, и наоборот).
- Политики по org_id и investigation_id через `current_setting('app.investigation_id', true)`. Общие справочники меток — отдельные таблицы без арендной привязки, для app только чтение.
- Сырые ответы провайдеров — JSONB с хешем содержимого и временем получения. Цепочка хешей — отдельная на расследование (advisory lock по id расследования).
- Бэкап — pgBackRest + restic в Backblaze B2 (G12); в этом аудите инструменты бэкапа и PITR не проверялись.
- Фиксированные затраты: $0 сверх уже оплаченного сервера (эталон G12 — 4 vCPU / 8 GB RAM); стоимость хранилища бэкапов — не проверено.
- Переменные затраты на стандартное расследование: около $0, платных вызовов нет.
- Компонентов, бесплатных только для разработки, нет: разработка идёт на том же образе в Docker Compose. Бесплатные планы Neon и Supabase для production непригодны (см. таблицу) и в схеме не используются.

### Ограничения и риски
- Единая точка отказа: в одной СУБД данные, очередь и события, и это единственная копия доказательной базы. RPO и RTO не заданы.
- Ошибка в пути тома или непроверенное восстановление означает потерю БД.
- Конкуренция за RAM с API, воркерами и IdP; всплеск задач очереди влияет на запросы API.
- Superuser или владелец таблицы может отключить триггеры: журнал обнаруживает подмену, но не исключает её.
- FK и unique обходят RLS: нельзя использовать пользовательские значения в уникальных ключах, общих между арендаторами.
- Системная БД DBOS хранит входы и выходы шагов вне RLS; транзакции, которые DBOS открывает сам (datasources, Custom Sessionmaker в 3.2.0), тоже обязаны выставлять контекст RLS.

### Как проверяем качество
- RLS: роль app с контекстом расследования A получает 0 строк расследования B по каждой таблице; транзакция без контекста возвращает 0 строк на каждом пути доступа, включая шаги воркера; app не владелец таблиц и не имеет BYPASSRLS.
- CI сверяет список таблиц с pg_class.relrowsecurity и relforcerowsecurity с ожидаемым: новая таблица без политики не проходит.
- Цель «100% фактов с TXID» закрепляется схемой: NOT NULL и CHECK на формат txid (64 hex) плюс внешний ключ факта на таблицу сырых транзакций.
- Миграции: в CI `alembic upgrade head` на чистой базе, затем downgrade и повторный upgrade.
- Журнал: UPDATE, DELETE и TRUNCATE ролью app завершаются ошибкой; периодическая задача пересчитывает цепочку по каждому расследованию и сверяет с головой, расхождение — инцидент.
- Голова цепочки включается в отчёт и при выпуске получает внешний штамп RFC 3161 (rfc3161-client 1.0.9 от 2026-09-14; согласуется с G11).
- Секреты: в журнал и логи подаётся подставной API-ключ, затем проверяется его отсутствие.
- Эксплуатация: тест «данные переживают docker compose down/up», еженедельное восстановление бэкапа на чистый контейнер, мониторинг размера системных таблиц очереди.

### Заменяемость
Движок — высокая в сторону managed Postgres при двух условиях: прямое (session) подключение и отсутствие вендорных расширений. Уход на другую СУБД — низкая: RLS, NOTIFY и JSONB используются осознанно, в MySQL и SQLite аналога RLS нет. ORM — средняя: модели привязаны к SQLAlchemy, схема и SQL-миграции переносимы. Драйвер — высокая (строка подключения SQLAlchemy). Журнал — обычные таблицы.

### Что проверить до фиксации выбора (Этап 2)
- Compose с томом на /var/lib/postgresql; критерий: данные на месте после docker compose down/up и пересоздания контейнера.
- Бэкап pgBackRest с восстановлением на чистый контейнер; критерий: укладываемся в RTO и RPO, которые задают владельцы.
- Прогон DBOS на postgres:18.6 в рамках spike раздела 8; критерий: все проверки spike пройдены.
- SQLAlchemy: старт на 2.0.54; переход на 2.1 — после прохождения тестов DBOS и собственных. Связка Alembic 1.20.0 + SQLAlchemy 2.0.54 в аудите отдельно не проверялась — не проверено; критерий: lock-файл разрешается, миграции проходят в CI.
- Драйвер: по умолчанию один psycopg 3 (его уже требует DBOS); asyncpg добавляется, только если замер покажет выигрыш.
- Накладные расходы RLS на запросах frontier-BFS (цель: 1 000 адресов за 5 минут) — не измерено, нужен замер.
- Выбор TSA для RFC 3161 и его стоимость — не проверено.
