## 10. Серверная часть и API

**Решение.** Python 3.13 для API, воркеров, трассировщика и агентов (G1); FastAPI 0.143, Pydantic 2 и uvicorn с версиями, закреплёнными lock-файлом; TypeScript — только веб-интерфейс, его клиент генерируется из OpenAPI. Вход: серверная часть — стандартный OIDC resource server (сама паролей не хранит и только проверяет токены), поставщик входа (IdP) заменяем; Keycloak рекомендуется при 16 GB памяти и более, при 8 GB — Logto, ZITADEL или внешний сервис после пробы на Этапе 2 (G14). Прогресс расследования передаётся в браузер потоком событий (SSE) поверх собственной таблицы событий. Статус: принято; поставщик входа — условно, до решения владельцев и пробы на сервере.

### Почему выбрано
- Вся предметная часть живёт в Python. По PyPI проверены версии tronpy 0.6.2 (MIT), web3 8.0.0, networkx 3.7, rustworkx 0.18.1, pydantic-ai 2.55.0, anthropic 1.13.0; совместимость с Python 3.13 по метаданным requires_python подтверждена для DBOS, SQLAlchemy, Alembic, networkx и tronpy, для остальных не проверена. Серверная часть на TypeScript потребовала бы второй среды исполнения либо отказа от этих библиотек.
- FastAPI — MIT, 0.143.0 от 2026-10-08, автогенерация OpenAPI и общие модели Pydantic для API и инструментов агентов; DBOS и pydantic-ai документируют интеграцию именно с FastAPI.
- SSE встроен в FastAPI (`fastapi/sse.py`, `EventSourceResponse`, документация с 0.135.0 от 2026-03-01). Чтением кода подтверждено: служебное сообщение для удержания соединения каждые 15 с, заголовки `Cache-Control: no-cache` и `X-Accel-Buffering: no`; в документации есть раздел про Last-Event-ID.
- Контракт OIDC и JWKS (набор открытых ключей поставщика) делает поставщика входа заменяемым: API зависит только от стандарта, код входа сами не пишем.
- Прогресс — однонаправленный поток: SSE работает поверх обычного HTTP, браузер сам переподключается, поле id даёт возобновление. Таблица событий с монотонным id одновременно служит журналом действий агентов (раздел 7).

### Лицензия и коммерческое использование
FastAPI, Pydantic, PyJWT и pydantic-ai — MIT: разрешено; условие MIT — сохранять уведомление об авторских правах и текст лицензии. uvicorn, Authlib и sse-starlette — BSD-3-Clause. Лицензии Pydantic и uvicorn проверены 2026-10-14 через GitHub API. Поставщики входа: Keycloak и Rauthy — Apache-2.0; Logto — MPL-2.0: по нашему прочтению, копилефт действует на уровне файлов и немодифицированный сервис обязательств не создаёт; ZITADEL — AGPL-3.0-only, причём его LICENSING.md возлагает определение соответствия на пользователя и рекомендует юриста. По нашему прочтению, коммерческое использование допустимо; ZITADEL — только как отдельный немодифицированный сервис и после оценки юриста. Условия использования внешних сервисов входа целиком не читались. Это прочтение инженера, а не заключение юриста.

- Ни один компонент не разворачивался; время ответа и потребление памяти не измерены.

### Инфраструктура и затраты
- Слои: обработчики FastAPI, сервисы, репозитории на SQLAlchemy; оркестрация — за интерфейсом JobRunner (раздел 8). ASGI-сервер — uvicorn 0.54.0. Разработка на Windows 11 идёт только в Docker Compose (Linux-контейнеры).
- Вход: веб-интерфейс использует Authorization Code + PKCE; API принимает только access-токены и проверяет iss, aud, exp и фиксированный список алгоритмов (PyJWT или Authlib); JWKS кэшируется и обновляется при неизвестном kid. Идентификаторы пользователя и организации из токена попадают в контекст транзакции для RLS; профили, организации и роли хранятся в PostgreSQL (раздел 7), пароли — только у поставщика входа. Программные API-ключи клиентов — отдельная таблица с хешами, не через поставщика входа.
- SSE: один слушатель LISTEN на процесс API на выделенном прямом соединении, вне пула соединений в режиме транзакций. NOTIFY отправляется объединённо — один сигнал на расследование не чаще N раз в секунду, в сообщении только id (лимит PostgreSQL — менее 8 000 байт); клиент дочитывает события из таблицы под RLS по Last-Event-ID. Команды (отмена, пауза) — обычные HTTP-запросы. Резерв — периодический опрос.
- Обратный прокси (Caddy по G12) обязан отдавать HTTP/2 и не буферизовать ответ: без HTTP/2 браузер ограничен 6 SSE-соединениями на домен (MDN).
- Фиксированные затраты: $0 за язык и фреймворк. Поставщик входа на своём сервере — $0 и память сервера: Keycloak 1.25–1.36 GB и ZITADEL около 512 MB (цифры из документации, нами не измерены); у Logto потребление памяти не измерено.
- Внешние сервисы входа (цены и лимиты прочитаны 2026-10-13/14): WorkOS AuthKit — $0 до 1 млн MAU, далее $2 500/мес за каждый следующий миллион; Clerk Pro — $25/мес, 50 000 MRU включено, далее $0.02 за MRU; ZITADEL Cloud Pro — $100/мес с 25 000 DAU.
- Бесплатные уровни с ограничениями: Clerk Hobby ($0) без MFA и passkeys — годится только для разработки; ZITADEL Cloud Free — до 100 DAU.
- Переменные затраты на стандартное расследование: $0.

### Ограничения и риски
- FastAPI в версии 0.x с очень частыми релизами: FastAPI, Starlette и Pydantic закрепляются lock-файлом вместе, обновление — по расписанию с прогоном контрактных тестов.
- Глобальная блокировка интерпретатора Python (GIL) ограничивает тяжёлые графовые расчёты в одном процессе: они выносятся в отдельные процессы или в rustworkx.
- На минимальной конфигурации G12 (8 GB на всё) Keycloak делит память с PostgreSQL, API, воркером и мониторингом; поместится ли он, не измерено (G14). Он же требует частых обновлений, а ошибка в настройке realm (области с пользователями и правилами входа) — риск безопасности. Смягчение: экспорт realm в репозиторий, минимальный набор сценариев входа, обязательная MFA для операторов.
- Внешний сервис входа: учётные данные у третьей стороны, вход зависит от внешнего сервиса, доступность оплаты в юрисдикции команды не проверена.
- NOTIFY в каждой транзакции записи события выстраивает фиксации транзакций в очередь (на это прямо ссылается код DBOS) и при массовой записи воркерами станет узким местом; поэтому сигнал отправляется объединённо.
- Встроенный SSE молод; досылку пропущенных событий по Last-Event-ID пишем сами.

### Как проверяем качество
- Контрактные тесты по OpenAPI-схеме; сгенерированный TypeScript-клиент собирается в CI при каждом изменении схемы.
- Негативные тесты токена: неверная подпись, алгоритм none, чужой issuer или audience, истёкший срок, неизвестный kid (должен вызывать обновление JWKS, а не отказ навсегда).
- Тесты ролей и принадлежности к расследованию вместе с RLS (раздел 7); токены и пароли не попадают в логи.
- Тест на секреты: подставной ключ не встречается ни в одном ответе API и ни в одной записи лога.
- SSE: после разрыва клиент переподключается с Last-Event-ID и получает ровно пропущенные события без дублей и пропусков; поток расследования A недоступен пользователю без доступа; каждое событие с фактом содержит TXID или явную пометку об отсутствии данных.

### Заменяемость
Фреймворк — средняя: при тонких обработчиках и сервисном слое переход на Litestar механический. Поставщик входа — высокая для серверной части (смена issuer и адреса JWKS), но перенос пользователей и хешей паролей — отдельная задача. Транспорт прогресса — высокая: формат событий свой, источник — таблица; встроенный SSE заменяется на sse-starlette или опрос без изменения источника.

### Что проверить до фиксации выбора (Этап 2)
- Решения владельцев: где хранятся учётные данные (свой сервер или внешний сервис), допустима ли AGPL (ZITADEL), нужны ли MFA и организации в MVP. Вариант по умолчанию — по G14: Keycloak при 16 GB и более (в том числе на рекомендуемой стартовой конфигурации 24 GB, G12), при 8 GB — Logto, ZITADEL или внешний сервис после пробы.
- Проба поставщика входа на сервере минимальной конфигурации (8 GB, G12): замер памяти Keycloak и Logto рядом с PostgreSQL, API, воркером и мониторингом; критерий — выбранный поставщик не вытесняет остальные сервисы и проходит негативные тесты токена.
- Если выбран внешний сервис: токены WorkOS AuthKit проходят чистую OIDC-проверку по JWKS, условия использования прочитаны, оплата доступна.
- SSE через Caddy: HTTP/2 включён, ответ не буферизуется, тест переподключения по Last-Event-ID пройден.
- Замер объединённого NOTIFY при массовой записи событий; критерий — событие доходит до интерфейса без роста времени фиксации транзакций у воркеров.
- Сквозной замер «простая транзакция за 30 с» через API, очередь и SSE — часть единого приёмочного замера на тестовом сервере с реальными источниками (протокол — раздел 13). Интервал: от старта задачи до проверенного JSON-отчёта в интерфейсе; PDF, подпись и метка времени — отдельная асинхронная задача со своей целью (её задают владельцы). В отчёт идут только данные, подтверждённые сетью (solidified): они отстают от цепочки на 18–19 блоков (54–57 с), поэтому для транзакции моложе примерно минуты ожидание подтверждения записывается отдельно как ожидание внешнего источника.
