## 4. Оркестрация AI-агентов

**Решение.** Собственный детерминированный оркестратор на DBOS Transact (durable workflows, очереди, HITL) и Pydantic AI для LLM-шагов в точках принятия решений; всё работает на том же PostgreSQL, без отдельного сервера оркестрации. Статус: условно принято — выбор фиксируется после spike на Этапе 2, где DBOS сравнивается с запасным вариантом без durable-движка (frontier-таблицы, мемоизирующий шлюз, Procrastinate).

### Почему выбрано
- Требования (детерминированный поток, 100% фактов с TXID, бюджет $1, лимиты источников) описывают durable-пайплайн с несколькими узкими LLM-вызовами, а не «автономных агентов». Бюджетные паузы, очереди с лимитами по источникам и доказательный журнал одновременно не даёт ни один из рассмотренных фреймворков — их пишем сами в любом случае.
- DBOS Transact — библиотека внутри процесса приложения: чекпоинт каждого шага в Postgres, recovery с последнего завершённого шага, очереди с `limiter` и concurrency, durable sleep, `send/recv` для approval и паузы по бюджету, `fork/rewind` для replay. Проверено по docs и исходному коду; код не запускался.
- Pydantic AI закрывает LLM-слой: нативные провайдеры (Anthropic, OpenAI) без LiteLLM, `FallbackModel`, валидация структурированного выхода, `UsageLimits` (подтверждено чтением `usage.py`), `TestModel/FunctionModel` для тестов без сети.
- Аудит независимо перепроверен: из 31 утверждения 20 подтверждены первичными источниками, 8 исправлены, 3 непроверяемы, целиком опровергнутых нет.
- Перепроверка нашла дефект исходной схемы (`agent.run()` с инструментами в одном шаге): по docs DBOS из шага нельзя вызывать, запускать или ставить в очередь workflow, поэтому вызовы инструментов обходили бы лимиты, а сбой посреди шага повторно оплачивал бы все его LLM-запросы. Зафиксировано: LLM-решения по умолчанию без инструментов, один запрос к модели = один `@DBOS.step`; инструменты остаются только у OSINT-агента (раздел 11).
- «Роли» агентов — типизированные функции `decide(Input) -> Output`; их выход — предложение, которое принимает или отклоняет детерминированный код. Проверка доказательств — не LLM, а детерминированная сверка по TXID.

### Лицензия и коммерческое использование
DBOS Transact — MIT, Pydantic AI — MIT; обе подтверждены чтением файлов LICENSE. Коммерческое SaaS-использование разрешено без условий. Зависимость Pydantic AI `httpx2` — BSD-3-Clause.

DBOS Conductor (консоль наблюдаемости, alerting, RBAC) — отдельный проприетарный продукт; библиотеке он не нужен и в MVP не используется. Self-hosted Conductor бесплатен только в Test/Development Mode; production с клиентскими данными требует платного ключа. Тарифы (прочитано 2026-10-14): Pro — $99/мес, Teams — $499/мес.

### Состояние проекта и расхождения «заявлено — на деле»
**DBOS Transact:** v3.2.0 от 2026-09-29, 1 626 звёзд, 6 open issues, 0 опубликованных advisories, CI с unit- и chaos-тестами. Расхождения:
- Recovery работает только при совпадении application version, которая по умолчанию равна hash кода workflow: после деплоя незавершённые расследования автоматически не продолжаются.
- `limiter` ограничивает число стартов workflow, а не HTTP-запросов; опрос очередей по умолчанию раз в 1.0 с; в 3.0.0 чинили регрессию limiter.
- Мажор 3.0.0 (2026-09-16) сменил схему системной БД и удалил admin server и in-memory queues.
- Заявлена работа на Windows, но CI идёт только на Ubuntu; запуск на Windows 11 — не проверено, разработка ведётся в Docker/WSL2.

**Pydantic AI:** v2.55.0 от 2026-10-09, 20 595 звёзд. Расхождения:
- Политика версий обещает отсутствие намеренных breaking changes в minor; фактический темп — 55 minor-релизов за 15.4 недели после v2.0.0 (2026-06-23), трёхмесячный порог для V3 пройден 2026-09-23.
- 16 опубликованных advisories, из них 4 high; два — о неполной редакции содержимого в OTel.
- `cost_limit` срабатывает после превышения и не действует для моделей без известных цен.
- `DBOSDurability` импортирует приватные модули DBOS, `DBOSAgent` помечен deprecated — готовую интеграцию не используем.

### Инфраструктура и затраты
- **Постоянные:** $0 за лицензии; новой инфраструктуры нет — системные таблицы DBOS лежат в том же PostgreSQL (отдельная схема и роль), воркер работает в процессе приложения.
- **Бесплатно только для разработки:** self-hosted Conductor. В production работаем без него: готового UI нет, состояние прогонов читается через `list_workflows` / `list_workflow_steps` и собственный журнал.
- **Переменные (LLM-токены).** Цены Claude API (прочитано 2026-10-14): Haiku 5.5 — $0.10/$0.50 за MTok (вход/выход) при промпте до 100k токенов, Sonnet 5.5 — $2/$10 за MTok. Допущение аудита (не измерено): 25 решающих вызовов по ~6k входных и ~1k выходных токенов — около $0.03 на Haiku 5.5 и $0.55 на Sonnet 5.5. С tool-loop (2–4 запроса на решение) и токенизатором новых моделей (~+30% токенов) Sonnet 5.5 на всех шагах дал бы $1.1–2.2, то есть выше лимита; Haiku 5.5 — менее $0.15. Поэтому перепроверка требует модель класса Haiku 5.5 по умолчанию и Sonnet 5.5 только на эскалациях; для такой маршрутизации аудит ожидает $0.05–0.30 на расследование (не измерено). Платные запросы к источникам данных учтены в их разделах.
- **Расхождение с общим решением по LLM:** там Sonnet 5.5 закреплён за планированием и финальным отчётом, что шире, чем «только эскалации». Стоимость этого варианта — не измерено; проверяется в spike (пункт 6 ниже).
- **Трудозатраты (оценка аудита, не измерено):** каркас оркестратора, бюджетный ledger, audit log и адаптер durable-слоя — 2–3 человеко-недели.

### Ограничения и риски
- **Recovery после деплоя:** нужны явная `application_version`, `enable_patching` и процедура деплоя при незавершённых прогонах.
- **Цели по времени** (30 с, 2 мин, 1 000 адресов за 5 мин) — не измерено: накладные расходы чекпоинтов и опроса очередей неизвестны.
- **Бюджет $1** держится только при дешёвой модели по умолчанию и собственном ledger, проверяющем лимит до каждого платного вызова; `cost_limit` Pydantic AI — лишь второй контур.
- **Изменчивость и цепочка поставок:** pin точных версий с хэшами и адаптеры-изоляторы обязательны; `httpx2` (первый релиз 2026-05-11) стоит на пути всех LLM-ключей.
- **Небольшой вендор:** у одного автора DBOS 394 коммита, у следующего — 77; UI есть только в Conductor, а его облачный вариант означает передачу метаданных расследований вендору.
- **Pickle по умолчанию:** право записи в системную БД равно исполнению кода при recovery, изменение классов ломает чекпоинты. Решение — portable JSON (`DBOSPortableJSONSerializer`), в шагах только ID и примитивы.

### Как проверяем качество
- Crash-тест: `kill -9` воркера посреди прогона; resume не повторяет оплаченные вызовы.
- Replay: HTTP- и LLM-ответы пишутся в content-addressed хранилище; прогон в режиме cache-only должен давать побитово тот же граф и отчёт.
- Не менее 50 сценариев с ground truth: детерминированный baseline против AI-слоя на одних fixtures; LLM-шаг остаётся только там, где он измеримо лучше.
- Тест бюджета: превышение лимита переводит прогон в `PAUSED_BUDGET` с сохранением результатов; после повышения лимита он продолжается.
- Тесты на prompt injection (имена токенов, memo, теги адресов, OSINT-страницы): план и метки не меняются.
- Тест утечек: поиск шаблонов ключей в логах, трассах и отчётах; полнота журнала вызовов сверяется со шлюзом (раздел 11).

### Заменяемость
Высокая при соблюдении изоляции. Durable-слой закрывается одним модулем-адаптером (декораторы workflow/step, очереди, `send/recv`): шаги — обычные Python-функции, модель workflow/step переносится на Temporal (workflow/activity). В запасном варианте без DBOS паузы, таймеры и лимиты пишутся самостоятельно; трудоёмкость такой замены — не измерено, оценивается в spike. LLM-слой изолируется интерфейсом `decide(Input) -> Output`: замена Pydantic AI на прямые SDK провайдеров, OpenAI Agents SDK или тонкие библиотеки (BAML, Instructor, Mirascope; у них нет встроенных `UsageLimits` и `TestModel`) затрагивает один модуль. Baseline-трассировщик не зависит ни от одной из библиотек.

### Что проверить до фиксации выбора (Этап 2)
Spike на 2–3 дня в Docker/WSL2 с реальным ключом TronGrid:
1. `kill -9` посреди прогона — критерий: 0 повторных платных вызовов после resume.
2. Деплой новой версии посреди прогона (явная `application_version`, `enable_patching`, чекпоинты в portable JSON) — критерий: расследование продолжается без ручного вмешательства.
3. Граф на 1 000 адресов — критерий: не более 5 минут; отдельно измерить накладные расходы чекпоинта и влияние `polling_interval_sec`.
4. Лимиты — критерий: 0 ответов 429 при заданном лимите провайдера (единый token bucket в шлюзе, раздел 11).
5. Тот же сценарий на варианте без DBOS; правило решения: если разница в надёжности не видна, берётся более простой вариант.
6. Замер числа запросов к модели и токенов на стандартное расследование для двух схем (Sonnet 5.5 только на эскалациях; Sonnet 5.5 на планировании и отчёте) — ориентир: LLM-часть не выше $0.30, верхней границы оценки аудита.
7. Решения владельцев: семантика бюджетного лимита (жёсткая остановка с частичным отчётом или пауза с запросом на повышение) и перечень действий, требующих approval человека.
