## 10. Серверная часть и API

**Решение.** Python 3.13 для API, воркеров, трассировщика и агентов (G1); FastAPI 0.143 + Pydantic 2 + uvicorn с версиями, закреплёнными lock-файлом; TypeScript — только UI, клиент генерируется из OpenAPI. Аутентификация: бэкенд — стандартный OIDC resource server, IdP выбирается по RAM и юрисдикции (G14). Прогресс расследования — SSE поверх собственной таблицы событий. Статус: принято; конкретный IdP ждёт решения владельцев и пробы на сервере.

### Почему выбрано
- Вся предметная часть живёт в Python. По PyPI проверены версии tronpy 0.6.2 (MIT), web3 8.0.0, networkx 3.7, rustworkx 0.18.1, pydantic-ai 2.55.0, anthropic 1.13.0; совместимость с Python 3.13 по requires_python подтверждена для DBOS, SQLAlchemy, Alembic, networkx и tronpy, для остальных — не проверено. TypeScript-бэкенд потребовал бы второго рантайма либо отказа от этих библиотек.
- FastAPI — MIT, 0.143.0 от 2026-10-08, автогенерация OpenAPI и общие Pydantic-модели для API и инструментов агентов; DBOS и pydantic-ai документируют интеграцию именно с FastAPI.
- SSE встроен в FastAPI (`fastapi/sse.py`, `EventSourceResponse`, документация с 0.135.0 от 2026-03-01). Чтением кода подтверждено: keep-alive ping каждые 15 с, заголовки `Cache-Control: no-cache` и `X-Accel-Buffering: no`; в документации есть раздел про Last-Event-ID.
- Контракт OIDC + JWKS делает IdP заменяемым: API зависит только от стандарта, код аутентификации сами не пишем.
- Прогресс — однонаправленный поток: SSE работает поверх обычного HTTP, браузер сам переподключается, поле id даёт возобновление. Таблица событий с монотонным id одновременно служит журналом действий агентов (раздел 7).

### Лицензия и коммерческое использование
FastAPI, PyJWT и pydantic-ai — MIT; Authlib и sse-starlette — BSD-3-Clause. Лицензии Pydantic и uvicorn в досье не зафиксированы — не проверено. IdP: Keycloak и Rauthy — Apache-2.0; Logto — MPL-2.0 (file-level copyleft, немодифицированный сервис не обременяет); ZITADEL — AGPL-3.0-only, причём LICENSING.md возлагает определение соответствия на пользователя и рекомендует юриста. Коммерческое использование допустимо; ZITADEL — только как отдельный немодифицированный сервис и после юридической оценки. ToS SaaS-провайдеров целиком не читались — не проверено.

### Инфраструктура и затраты
- Слои: handlers (FastAPI) -> services -> repositories (SQLAlchemy); оркестрация — за интерфейсом JobRunner (раздел 8). ASGI-сервер — uvicorn 0.54.0. Разработка на Windows 11 идёт только в Docker Compose (Linux-контейнеры).
- Аутентификация: UI использует Authorization Code + PKCE; API принимает только access-токены и проверяет iss, aud, exp и фиксированный список алгоритмов (PyJWT или Authlib), JWKS кэшируется с обновлением по неизвестному kid. Идентификаторы пользователя и организации из токена попадают в контекст транзакции для RLS. Программные API-ключи клиентов — отдельная таблица с хешами, не через IdP.
- SSE: один слушатель LISTEN на процесс API на выделенном прямом соединении вне transaction-пула. NOTIFY шлётся коалесцированно — один сигнал на расследование не чаще N раз в секунду, payload только id (лимит < 8000 байт); клиент дочитывает события из таблицы под RLS по Last-Event-ID. Команды (отмена, пауза) — обычные HTTP-запросы. Резерв — периодический опрос.
- Reverse proxy (Caddy по G12) обязан отдавать HTTP/2 и не буферизовать ответ: без HTTP/2 браузер ограничен 6 SSE-соединениями на домен (MDN).
- Фиксированные затраты: $0 за язык и фреймворк. IdP self-hosted — $0 и память сервера: Keycloak 1250–1360 MB и ZITADEL около 512 MB (цифры из документации, не измерено), Logto — не измерено.
- IdP как SaaS (цены и лимиты прочитаны 2026-10-13/14): WorkOS AuthKit — $0 до 1M MAU, далее $2 500/мес за каждый следующий миллион; Clerk Pro — $25/мес, 50 000 MRU включено, далее $0.02 за MRU; ZITADEL Cloud Pro — $100/мес с 25 000 DAU.
- Бесплатные уровни с ограничениями: Clerk Hobby ($0) без MFA и passkeys — годится только для разработки; ZITADEL Cloud Free — до 100 DAU.
- Переменные затраты на стандартное расследование: $0.

### Ограничения и риски
- FastAPI в версии 0.x с очень частыми релизами: FastAPI, Starlette и Pydantic закрепляются lock-файлом вместе, обновление — по расписанию с прогоном контрактных тестов.
- GIL ограничивает CPU-тяжёлый графовый анализ в одном процессе: такие расчёты выносятся в процессы-воркеры или rustworkx.
- Эталонный сервер G12 — ровно 8 GB на всё: Keycloak займёт место рядом с PostgreSQL, API, воркером и стеком наблюдаемости; хватит ли памяти — не измерено. Он же требует частых обновлений, а неверная конфигурация realm — типовой источник уязвимостей. Смягчение: экспорт realm в репозиторий, минимальный набор flows, обязательная MFA для операторов.
- SaaS IdP: учётные данные у третьей стороны, вход зависит от внешнего сервиса, доступность оплаты в юрисдикции команды — не проверено.
- NOTIFY в каждой транзакции записи события сериализует commit-ы (на это прямо ссылается код DBOS) и при массовой записи воркерами станет узким местом.
- Встроенный SSE молод; досылку пропущенных событий по Last-Event-ID пишем сами.

### Как проверяем качество
- Контрактные тесты по OpenAPI-схеме; сгенерированный TypeScript-клиент собирается в CI при каждом изменении схемы.
- Негативные тесты токена: неверная подпись, алгоритм none, чужой issuer или audience, истёкший срок, неизвестный kid (должен вызывать обновление JWKS, а не отказ навсегда).
- Тесты ролей и принадлежности к расследованию вместе с RLS (раздел 7); токены и пароли не попадают в логи.
- Тест на секреты: подставной ключ не встречается ни в одном ответе API и ни в одной записи лога.
- SSE: после разрыва клиент переподключается с Last-Event-ID и получает ровно пропущенные события без дублей и пропусков; поток расследования A недоступен пользователю без доступа; каждое событие с фактом содержит TXID или явную пометку об отсутствии данных.

### Заменяемость
Фреймворк — средняя: при тонких обработчиках и сервисном слое переход на Litestar механический. IdP — высокая для бэкенда (смена issuer и JWKS URL), но перенос пользователей и хешей паролей — отдельная задача. Транспорт прогресса — высокая: формат событий свой, источник — таблица; встроенный SSE заменяется на sse-starlette или опрос без изменения источника.

### Что проверить до фиксации выбора (Этап 2)
- Решения владельцев: место хранения учётных данных, допустимость AGPL, MFA и организации в MVP.
- Проба IdP на эталонном сервере: замер RAM Keycloak и Logto рядом с PostgreSQL, API и воркером; критерий — выбранный IdP не вытесняет остальные сервисы и проходит негативные тесты токена.
- Если выбран SaaS: токены WorkOS AuthKit проходят чистую OIDC-проверку по JWKS, ToS прочитаны, оплата доступна.
- SSE через Caddy: HTTP/2 включён, ответ не буферизуется, тест переподключения по Last-Event-ID пройден.
- Замер коалесцированного NOTIFY при массовой записи событий; критерий — событие доходит до UI без роста времени commit у воркеров.
- Сквозной замер «простая транзакция <= 30 с» через API, очередь и SSE.
